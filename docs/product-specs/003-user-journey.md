# NextStep 用户旅程

状态：P1 草案，待用户会签  
记录日期：2026-07-07  
上游真源：`docs/product-specs/002-complete-project-blueprint.md`

## 1. 核心旅程

NextStep 的核心旅程是：

```text
我有一个想法
↓
系统帮我补全成项目
↓
系统帮我冻结项目真源
↓
系统帮我拆成版本路线
↓
系统帮我拆成模块闭环
↓
系统生成执行任务包
↓
Agent 或用户执行
↓
系统验收结果
↓
系统处理变更
↓
项目交付归档
```

## 2. 角色

### 2.1 用户

用户负责提供目标、业务背景、取舍判断和最终确认。

用户不需要一开始就会写 PRD、Prompt、技术方案或测试标准。

### 2.2 NextStep

NextStep 负责把用户的表达整合成项目结构，持续维护项目状态，并在关键节点阻止项目漂移。

### 2.3 执行 Agent

执行 Agent 负责按任务包完成具体产出。它不能自行扩大范围，也不能绕过验收门禁。

## 3. 旅程阶段

| 阶段 | 用户状态 | NextStep 动作 | 输出物 | 硬性完成条件 |
|---|---|---|---|---|
| 1. 需求入口 | 只有模糊想法 | 提取目标、场景、约束、缺口 | 原始需求记录 | 用户确认需求被正确理解 |
| 2. 项目成型 | 不知道完整项目长什么样 | 整合目标用户、范围、非目标、成功指标 | 项目总 Spec | 项目真源完整且可验收 |
| 3. 版本规划 | 不知道第一版做什么 | 拆 V1、V2、Backlog | 版本路线图 | V1 有独立闭环价值 |
| 4. 模块拆解 | 项目仍然太大 | 按业务闭环拆模块 | 模块闭环清单 | 每个模块有输入、输出、DoD |
| 5. 执行准备 | 不知道怎么让 Agent 做 | 生成执行任务包 | 执行任务包 | 任务包绑定范围和验收 |
| 6. 执行进行 | Agent 开始产出 | 维护当前模块状态 | 过程记录 | 不允许偷渡新需求 |
| 7. 结果验收 | 不知道结果是否对 | 对照 DoD 验收 | 验收报告 | 通过、退回、延期或变更明确 |
| 8. 变更分流 | 发现新需求 | 分类进入当前缺口、后续版本、Backlog 或拒绝 | Change Request | 不污染当前闭环 |
| 9. 交付归档 | 准备完成阶段 | 固化交付物和风险 | 交付清单 | 证据可追溯 |

## 4. 关键使用场景

### 4.1 用户只有一句想法

输入：

```text
我想做一个 AI 项目推进工具。
```

NextStep 输出：

- 原始意图。
- 深层问题。
- 目标用户假设。
- 核心场景假设。
- 待确认问题。
- 推荐的项目定义。
- 是否允许进入项目成型。

### 4.2 用户想直接让 Agent 开发

NextStep 应阻止直接开发，并提示当前缺少：

- 项目真源。
- 版本边界。
- 模块闭环。
- 验收指标。

只有补齐后才能生成执行任务包。

### 4.3 用户中途提出新需求

输入：

```text
那顺便支持团队协作吧。
```

NextStep 输出：

- 新需求类型。
- 是否影响当前阶段 DoD。
- 影响范围。
- 建议分流结论。
- 是否需要用户确认更新路线锁。

### 4.4 Agent 结果跑偏

NextStep 不只是重新生成 Prompt，而是判断跑偏原因：

- 需求真源不完整。
- 版本边界错误。
- 模块拆解过大。
- 执行任务包不清晰。
- Agent 没遵守非目标。
- 验收指标不够硬。

然后把项目退回正确节点。

## 5. 用户感知目标

用户在使用 NextStep 时，应该始终能回答：

- 我现在在哪个阶段。
- 当前版本要交付什么。
- 当前模块要完成什么。
- 哪些东西明确不做。
- 当前结果是否通过。
- 下一步该做什么。
- 新想法应该放在哪里。

## 6. 旅程非目标

本阶段不定义具体 UI 页面，不定义技术实现，也不定义 Agent 调用协议。

这些内容应在后续 S2 原型与设计、S3 技术架构和 P3 执行机制设计中建立。
