# NextStep 完整项目蓝图

状态：P1 已会签
记录日期：2026-07-07
上游真源：`docs/product-specs/001-original-requirement.md`
路线锁：`PROJECT_ROUTE_LOCK.md`

## 1. 项目定义

NextStep 是一个 AI 项目闭环落地系统。它帮助用户把模糊想法整合成完整项目真源，再拆成版本路线和多个可量化、可执行、可验收的小闭环，并通过阶段门禁、执行任务包、验收指标和变更管理，推动项目从需求、开发到验收交付持续落地。

NextStep 的核心不是替用户写更好的 Prompt，而是让用户在使用 AI 做项目时始终拥有一个稳定的项目控制层。

## 2. 产品判断

NextStep 值得做的原因是：AI 执行能力正在变强，但普通用户和小团队缺少把想法组织成可持续执行项目的能力。

现有 AI 对话工具擅长回答和执行单次任务，却容易丢失需求边界、阶段状态和验收标准。传统项目管理工具擅长记录任务，却不擅长把模糊想法变成完整项目结构。NextStep 的机会点在两者之间：

> 用产品经理式的需求整合、阶段门禁和闭环拆解，把 AI 的开放式对话变成可交付项目。

## 3. 目标用户

### 3.1 核心用户

NextStep 首先服务个人用户和小团队负责人。

典型用户包括：

- 有想法但不擅长拆解项目的创业者。
- 会使用 AI，但经常让 AI 执行跑偏的独立开发者。
- 想借助 AI 完成产品、文档、流程优化或内容项目的产品经理。
- 需要把业务想法变成可执行方案的企业管理者。
- 需要从创意走到交付的内容创作者或咨询顾问。

### 3.2 用户共同特征

- 知道自己想要一个结果，但不知道如何定义完整路径。
- 能描述模糊目标，但容易遗漏范围、约束、非目标和验收标准。
- 经常把 AI 当执行者使用，却缺少项目状态管理。
- 容易陷入“不断改 Prompt、不断加需求、不断重做”的循环。

## 4. 核心问题

| 问题 | 用户表现 | 项目后果 | NextStep 解决方式 |
|---|---|---|---|
| 原始需求不完整 | 用户只说一个想法 | Agent 按字面执行，结果跑偏 | 先做需求补全与产品定义 |
| 第一版边界不清 | 什么都想做 | 无法形成闭环 | 建立版本锁 |
| 缺少验收标准 | 做完不知道算不算完成 | Agent 持续开发 | 建立闭环锁 |
| 新需求随时插入 | 聊着聊着范围变大 | 当前阶段失控 | 建立变更分流 |
| MVP 替代完整路线 | 只知道先做一点 | 项目后续断档 | 先建完整蓝图再切版本 |
| 项目状态丢失 | 每次对话像重新开始 | 决策和上下文不可维护 | 维护项目真源 |

## 5. 产品核心原则

- 原始需求不能直接进入执行，必须先整合成完整项目。
- AI 理解需求的目的不是替用户做决定，而是补全、澄清并记录需求。
- 需求讨论完成后，必须先冻结需求真源，再从产品经理视角构建产品。
- 产品定义不能直接进入开发，必须先形成产品原型并经用户会签。
- UI 设计必须基于已会签产品原型，并形成可用于还原验收的设计真源。
- 技术选型与架构必须基于已确认的产品定义、原型和设计真源。
- 完整项目不能直接进入开发，必须先拆成版本路线、大里程碑和小里程碑。
- 小里程碑不能直接执行，必须先绑定输入、输出、DoD、测试方式、非目标和验收方式。
- 新需求不能直接并入当前小里程碑，必须先进入变更分流。
- 阶段未通过验收，不允许进入下一阶段。
- MVP 只是完整路线里的第一个可交付版本，不是产品思考的终点。

## 6. 完整项目流程

```text
原始需求
↓
意图理解
↓
需求补全与讨论
↓
需求记录与冻结
↓
产品经理视角整合
↓
完整项目蓝图
↓
产品定义 / PRD
↓
产品原型
↓
用户原型会签
↓
UI 设计效果图
↓
设计真源会签
↓
技术选型与架构
↓
版本路线
↓
大里程碑
↓
小里程碑闭环
↓
执行任务包
↓
Agent 执行
↓
小里程碑测试验收
↓
合入大里程碑
↓
大里程碑集成验收
↓
UI 还原验收
↓
产品定义验收
↓
交付验收
↓
交付归档
```

变更分流贯穿全流程：

```text
新需求 / 漏项 / 设计变更 / 技术风险 / 验收失败
↓
变更分流
↓
当前阶段缺口 / 后续版本 / Backlog / 路线变更 / 拒绝
↓
更新对应真源后再继续
```

这个流程的关键是：NextStep 每一步都必须产生可追溯交付物，而不是只产生聊天回复。

## 7. 核心对象

| 对象 | 含义 | 必须回答的问题 | 典型交付物 |
|---|---|---|---|
| Project | 完整项目真源 | 这个项目为什么存在，解决谁的问题 | 产品定义 / PRD |
| Requirement Set | 需求记录与冻结 | 用户和 AI 讨论后确认了哪些需求 | 需求清单 |
| Product Definition | 产品经理视角的产品定义 | 产品到底做什么、不做什么、如何验收 | PRD |
| Prototype | 产品原型真源 | 用户是否认可产品结构和关键流程 | 原型与会签记录 |
| Design Source | UI 设计真源 | 开发后如何判断是否还原设计 | 高保真设计稿 |
| Technical Plan | 技术选型和架构真源 | 怎么实现、风险在哪里、如何回滚 | 架构方案 |
| Version | 一个可交付版本 | 当前版本交付什么，不交付什么 | 版本路线图 |
| Major Milestone | 大里程碑 | 一组能力什么时候可集成验收 | 大里程碑计划 |
| Small Milestone | 小里程碑闭环 | 本单元完成后用户得到什么 | 小里程碑闭环卡 |
| Stage | 当前阶段和门禁 | 现在在哪，能否进入下一阶段 | 阶段门禁记录 |
| Deliverable | 交付物和证据 | 用什么证明已经完成 | 验收报告 |
| Change Request | 变更入口 | 新需求是否影响当前闭环 | 变更分流记录 |
| Execution Packet | 执行任务包 | Agent 要按什么边界执行 | 执行指令包 |

术语约定：小里程碑是当前阶段对可执行模块的正式命名。若文档中出现“模块”一词，仅作为通俗描述；路线、验收和执行任务包一律以“小里程碑”为准。

## 8. 核心能力地图

NextStep 的完整能力分为 16 个系统模块。

| 模块 | 解决的问题 | 输入 | 输出 | 硬性闭环指标 |
|---|---|---|---|---|
| 1. 需求入口 | 用户表达模糊 | 一段自然语言想法 | 原始需求记录 | 能提取目标、场景、约束和缺口 |
| 2. 需求补全与冻结 | 需求讨论后没有沉淀 | 原始需求和补充讨论 | 需求清单 | 用户确认当前需求真源 |
| 3. 产品定义 | 需求没有产品化 | 需求清单 | PRD / 产品定义 | 目标用户、核心流程、非目标和验收标准齐全 |
| 4. 原型管理 | 需求直接进入设计或开发 | 产品定义 | 产品原型 | 用户确认产品结构和关键交互 |
| 5. UI 设计真源 | 开发后无法判断还原度 | 已会签原型 | UI 设计稿 | UI 验收标准明确 |
| 6. 技术选型与架构 | 开发前技术路线不清 | 产品定义和设计真源 | 技术方案 | 技术栈、数据模型、风险和回滚方案明确 |
| 7. 真源管理 | 项目状态丢失 | 已确认决策 | 项目真源 | 后续执行必须引用真源 |
| 8. 版本规划 | 第一版边界不清 | 产品定义 / PRD | 版本路线图 | V1、V2、Backlog 边界明确 |
| 9. 大里程碑规划 | 完整版本无法推进 | 版本路线 | 大里程碑计划 | 每个大里程碑可集成、可验收 |
| 10. 小里程碑拆解 | 大里程碑无法执行 | 大里程碑计划 | 小里程碑清单 | 每个小里程碑有输入、输出、DoD、测试方式 |
| 11. 阶段门禁 | 阶段未达标仍继续推进 | 阶段状态和交付物 | 通过、退回、需讨论或阻塞 | 未达标不得进入下一阶段 |
| 12. 执行任务包 | Agent 执行跑偏 | 当前小里程碑 | 执行指令包 | 执行任务绑定范围、测试方式和验收方式 |
| 13. 测试与合入验收 | 做完不知道能否合入 | 小里程碑结果 | 测试和合入结论 | 测试通过后才能合入大里程碑 |
| 14. UI 与产品验收 | 功能完成但不符合设计或产品定义 | 大里程碑结果 | UI 验收和产品验收报告 | 设计还原和产品定义均通过 |
| 15. 变更分流 | 新需求污染当前版本 | 新需求、漏项或验收失败 | Change Request | 新需求被分流，不污染当前闭环 |
| 16. 交付归档 | 结果不可追溯 | 已验收交付物 | 交付清单 | 交付证据和风险可追溯 |

## 9. 三把锁

### 9.1 需求锁

需求锁用于防止模糊想法直接进入执行。

通过条件：

- 项目目标已确认。
- 目标用户已确认。
- 核心场景已确认。
- 项目范围已确认。
- 非目标已确认。
- 成功指标已确认。
- 用户明确同意进入版本规划。

### 9.2 版本锁

版本锁用于防止完整项目一次性失控。

通过条件：

- V1 有独立交付价值。
- V1 范围小于完整项目范围。
- V1 不做事项明确。
- V2 和 Backlog 不污染 V1。
- V1 完成后能形成可演示、可验收、可继续迭代的结果。

### 9.3 闭环锁

闭环锁用于防止 Agent 持续开发。

通过条件：

- 当前小里程碑有明确输入。
- 当前小里程碑有明确输出。
- 当前小里程碑有 Definition of Done。
- 当前小里程碑有验收方法。
- 当前小里程碑有失败处理入口。
- 当前小里程碑有明确非目标。

## 10. 阶段门禁

| 阶段 | 目的 | 交付物 | 通过门禁 | 不允许提前做 |
|---|---|---|---|---|
| S0 需求入口 | 记录和分流原始需求 | 原始需求记录 | 需求被接受、延后、拒绝或转入变更 | 不生成开发任务 |
| S1 需求冻结与产品定义 | 明确做什么和为什么做 | 需求清单、PRD、用户旅程、能力地图 | 产品范围可验收 | 不选技术栈 |
| S2 产品原型 | 明确页面结构、主流程和关键交互 | 原型、页面结构、交互说明 | 用户会签原型 | 不进入 UI 设计细化 |
| S3 UI 设计真源 | 明确视觉、组件和还原标准 | UI 效果图、设计规范、UI 验收标准 | 设计不可偏离项明确 | 不进入工程实现 |
| S4 技术架构 | 明确怎么实现 | 架构、技术栈、数据模型 | 技术风险可验证 | 不大范围编码 |
| S5 里程碑计划 | 拆成可验收闭环 | 版本路线、大里程碑、小里程碑、DoD | 当前阶段可执行 | 不跳过小里程碑验收 |
| S6 小里程碑开发 | 实现当前小里程碑 | 代码、配置、测试 | 小里程碑测试通过 | 不合入未验收结果 |
| S7 大里程碑集成 | 合入并验证一组能力 | 集成结果、回归证据 | 大里程碑集成验收通过 | 不跳过 UI 和产品验收 |
| S8 UI 与产品验收 | 判断是否符合设计和产品定义 | UI 验收报告、产品验收报告 | 设计还原和产品定义均通过 | 不继续暗改范围 |
| S9 交付归档与变更管理 | 固化成果，管理后续变化 | 交付清单、归档记录、Backlog、Change Request | 证据可追溯，新需求被分流 | 不污染历史验收 |

## 11. 关键用户场景

### 11.1 从模糊想法到完整项目

用户输入：

```text
我想做一个工具，让 AI 在对话前帮我生成更好的提示词。
```

NextStep 不直接生成提示词，而是先判断：

- 表层需求是什么。
- 深层问题是什么。
- 是否只是 Prompt 问题。
- 完整项目应该解决哪些环节。
- 当前版本应该交付什么闭环。

### 11.2 从完整项目到版本路线

用户确认完整项目后，NextStep 输出：

- V1：能让用户创建项目，完成需求补全、需求冻结、产品定义和初步版本路线。
- V2：增加产品原型会签、UI 设计真源、技术选型和大/小里程碑拆解。
- V3：增加执行任务包、小里程碑测试验收、大里程碑集成验收、UI 验收、产品验收和交付归档。
- Backlog：Agent 市场、复杂工作流编排、知识库平台等。

本节只表达产品方向和版本切分假设，不冻结最终版本路线。P3 版本与里程碑拆解时，必须重新审查 V1、V2、V3 和 Backlog 的边界、依赖、验收标准和失败判定。

这里的 V1 不是随便做个 MVP，而是完整项目路线里的第一个可交付版本。

### 11.3 从小里程碑执行到验收

用户选择一个小里程碑后，NextStep 必须生成执行任务包：

- 背景。
- 当前小里程碑目标。
- 输入材料。
- 输出格式。
- 明确非目标。
- 验收标准。
- 失败处理方式。

Agent 返回结果后，NextStep 不继续开发，而是先验收。

### 11.4 新需求出现时

用户说：

```text
顺便加一个多 Agent 编排吧。
```

NextStep 应先判断：

- 是否影响当前版本 DoD。
- 是否是当前阶段缺口。
- 是否属于后续阶段需求。
- 是否需要更新路线锁。
- 是否应该进入 Backlog。

## 12. 产品不做什么

NextStep 当前不做：

- 不做单纯 Prompt 优化器。
- 不做传统项目管理看板。
- 不做 Agent 市场。
- 不做复杂多 Agent 编排平台。
- 不做大而全知识库系统。
- 不做只会输出一次性 MVP 的工具。
- 不允许无门禁、无验收地持续开发。

## 13. 成功指标

### 13.1 用户成功指标

- 用户能把一句模糊想法转成完整项目真源。
- 用户能知道当前项目处于哪个阶段。
- 用户能知道下一步该做什么。
- 用户能判断当前成果是否通过验收。
- 用户能把新增需求正确放入当前版本、后续版本或 Backlog。

### 13.2 项目成功指标

- 每个项目都有产品定义 / PRD。
- 每个版本都有范围、非目标和验收标准。
- 每个小里程碑都有输入、输出、DoD、测试方式和验收方法。
- 每次 Agent 执行都有执行任务包。
- 每次阶段切换都有门禁记录。
- 每个新需求都有分流结论。

### 13.3 产品质量指标

- 项目漂移次数下降。
- 反复改 Prompt 的次数下降。
- 用户从想法到可执行小里程碑的时间下降。
- 小里程碑验收通过率提升。
- 用户对“当前在哪、下一步是什么”的理解稳定。

上述指标在 P1 只定义方向。P3 必须为每个指标补充统计口径、阈值、样例、失败判定和验收矩阵，避免“可量化闭环”停留在描述层。

## 14. 失败边界

NextStep 必须能识别以下失败，并把项目退回正确节点：

| 失败类型 | 表现 | 回退节点 |
|---|---|---|
| 需求不完整 | 用户目标、场景、约束不清 | 需求入口 |
| 项目定义错误 | 产品定位跑偏 | 产品定义 |
| 版本边界过大 | V1 无法闭环 | 版本规划 |
| 小里程碑拆解过粗 | 单个小里程碑无法验收 | 小里程碑拆解 |
| 执行结果偏离 | Agent 输出不符合任务包 | 执行任务包 |
| 验收指标过软 | 无法判断是否完成 | 阶段门禁 |
| 新需求污染 | 当前小里程碑范围变大 | 变更分流 |

## 15. 产品形态判断

NextStep 的最终形态更接近项目驾驶舱，而不是聊天软件。

核心界面应该优先展示：

- 当前项目。
- 当前阶段。
- 当前版本。
- 当前小里程碑。
- 当前交付物。
- 当前风险。
- 下一步行动。
- 阶段门禁状态。

聊天框是辅助入口，不是产品中心。

## 16. P1 结论

NextStep 的完整项目蓝图可以冻结为：

> NextStep 通过需求真源、产品定义、产品原型、设计真源、技术方案、版本路线、大里程碑、小里程碑、阶段门禁、执行任务包、测试验收、UI 验收、产品验收和变更分流，把用户的模糊想法组织成可持续交付的项目系统。

P1 通过后，下一步应进入 P2：版本与里程碑拆解。
