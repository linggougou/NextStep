## 1. 契约目标

本文只定义后续真源文档的结构、字段、合格标准和禁止提前内容。

它不是：

- UI 高保真设计稿。
- 技术架构方案。
- 版本路线图。
- 大里程碑或小里程碑拆解。
- 真实验收报告。

本文的作用是让后续 S3、S4、P3 和验收阶段都有固定文档轨道，避免 Agent 自由发挥、跳阶段或把草稿包装成正式真源。

## 2. 通用文档规则

每份后续真源文档必须包含：

| 字段 | 要求 |
|---|---|
| 状态 | 草稿、待会签、已会签、退回、已归档之一 |
| 记录日期 | 使用明确日期 |
| 所属阶段 | 绑定生命周期阶段和里程碑 |
| 上游真源 | 明确引用依赖文档 |
| 文档目标 | 说明本文解决什么问题 |
| 明确非目标 | 说明本文不做什么 |
| 必填内容 | 按对应契约逐项填写 |
| 不可偏离项 | 后续执行不能突破的边界 |
| 验收标准 | 如何判断本文合格 |
| 变更入口 | 修改已会签内容时走哪个 Change Request |

通用禁止项：

- 不得把草稿标记为已会签。
- 不得缺少上游真源引用。
- 不得用聊天摘要替代结构化字段。
- 不得在未会签前允许进入下一阶段。
- 不得在格式契约中提前写入真实 UI、技术栈、版本路线或验收结论。

## 3. S3 UI 设计真源格式

### 3.1 文档定位

S3 UI 设计真源用于约束后续 UI 还原验收。

它必须回答：

- 页面长什么样。
- 页面有哪些状态。
- 组件如何表现。
- 响应式如何处理。
- 开发后如何判断是否还原设计。

### 3.2 必填字段

| 字段 | 内容要求 | 合格标准 |
|---|---|---|
| 页面清单 | 列出所有需要设计的页面 | 覆盖 P2 产品原型中的核心页面 |
| 页面目标 | 每个页面解决什么用户问题 | 目标能对应用户旅程或阶段门禁 |
| 核心状态 | 每个页面有哪些业务状态 | 至少覆盖默认、待会签、阻塞、退回等关键状态 |
| 关键交互 | 用户如何完成主要动作 | 交互能对应原型主流程 |
| 组件状态表 | 组件在不同状态下的表现 | 阶段卡、交付物卡、会签按钮、风险提示、变更项必须覆盖 |
| 响应式要求 | 桌面、平板、移动端布局规则 | 不能把移动端退化成单一聊天流 |
| 空状态 | 无项目、无交付物、无变更时如何展示 | 必须包含引导下一步 |
| 错误状态 | 加载失败、保存失败、权限不足等 | 必须包含恢复方式 |
| 阻塞状态 | 门禁未通过、缺少真源、需用户确认等 | 必须说明为什么不能继续 |
| UI 验收清单 | 后续 UI 还原验收如何检查 | 可以逐页面、逐组件核验 |
| 不可偏离项 | 不允许开发偏离的视觉和交互边界 | 与 P2 原型不可偏离项一致 |

### 3.3 禁止提前写入

S3 文档不得写入：

- 技术栈选择。
- API 设计。
- 数据库模型。
- 版本路线。
- 大里程碑或小里程碑拆解。
- 执行任务包。

## 4. S4 技术架构文档格式

### 4.1 文档定位

S4 技术架构文档用于说明 NextStep 如何被实现、为什么选择该技术路线、关键风险如何验证，以及失败时如何回滚。

### 4.2 必填字段

| 字段 | 内容要求 | 合格标准 |
|---|---|---|
| 技术目标 | 技术方案要支撑哪些产品能力 | 必须服务项目真源、阶段门禁、交付物和变更分流 |
| 候选技术栈 | 列出可选方案 | 至少包含推荐方案和备选方案 |
| 不选原因 | 说明未采用方案的理由 | 理由必须基于项目约束，而不是偏好 |
| 数据模型草案 | 定义核心对象关系 | 至少覆盖 Project、Stage、Deliverable、Change Request、Milestone |
| 阶段门禁模型 | 定义状态和推进规则 | 必须覆盖通过、退回、需讨论、阻塞 |
| 状态机模型 | 定义关键对象状态变化 | 会签后的真源不能被直接覆盖 |
| AI 交互边界 | AI 能建议什么、不能自动决定什么 | 涉及阶段推进和真源冻结必须用户确认 |
| 权限与数据安全 | 用户、项目、交付物和敏感信息边界 | 至少说明访问控制和数据保护原则 |
| 风险验证计划 | 高风险假设如何验证 | 每个高风险点有验证方式和失败标准 |
| 回滚方案 | 技术路线失败时如何退回 | 有迁移、替代或延期方案 |

### 4.3 禁止提前写入

S4 文档不得写入：

- 未经 S3 会签的 UI 设计结论。
- 未经 P3 会签的版本路线和小里程碑。
- 具体开发任务包。
- 真实代码实现。
- 发布计划。

## 5. P3 版本与里程碑拆解格式

### 5.1 文档定位

P3 文档用于把完整项目拆成版本路线、大里程碑和小里程碑闭环。

它必须解决：

- 第一版到底落地什么。
- 后续版本放什么。
- 每个大里程碑如何集成验收。
- 每个小里程碑如何执行、测试和退回。

### 5.2 必填字段

| 字段 | 内容要求 | 合格标准 |
|---|---|---|
| V1 边界 | V1 包含什么、不包含什么 | V1 有独立交付价值，且范围小于完整项目 |
| V2 边界 | V2 承接哪些后续能力 | V2 不污染 V1 验收 |
| Backlog 边界 | 后置或不做事项 | 能解释为什么不进当前版本 |
| 大里程碑目标 | 每个大里程碑交付什么能力 | 每个大里程碑可集成、可验收 |
| 大里程碑范围 | 包含哪些能力和交付物 | 范围不与其他大里程碑重叠 |
| 大里程碑验收标准 | 通过条件和失败条件 | 能判断是否可进入 UI / 产品验收 |
| 小里程碑输入 | 开始前需要哪些真源和材料 | 缺输入不得执行 |
| 小里程碑输出 | 完成后必须产出什么 | 输出必须可测试、可验收 |
| 小里程碑 DoD | 完成定义 | 不能使用“基本完成”等软描述 |
| 测试方式 | 如何验证小里程碑 | 至少有本地验证、文档验证或人工验收方式 |
| 明确非目标 | 当前小里程碑不做什么 | 防止顺手扩展 |
| 依赖关系 | 小里程碑之间的先后关系 | 依赖不清不得进入执行任务包 |
| 验收矩阵 | 版本、大里程碑、小里程碑和验收项对应关系 | 每个验收项有口径、阈值、证据和失败判定 |
| 失败 / 退回规则 | 不通过时回到哪里 | 必须能定位回需求、原型、设计、技术或小里程碑 |

### 5.3 禁止提前写入

P3 文档不得写入：

- 未经 S3 会签的 UI 设计细节。
- 未经 S4 会签的具体技术实现。
- 真实代码任务。
- 测试通过结论。
- 发布或交付归档结论。

## 6. 后续验收报告格式

### 6.1 文档定位

验收报告用于判断某个阶段、交付物、大里程碑或小里程碑是否允许进入下一阶段。

验收报告不是总结稿，而是门禁证据。

### 6.2 必填字段

| 字段 | 内容要求 | 合格标准 |
|---|---|---|
| 验收对象 | 被验收的阶段、交付物或里程碑 | 对象唯一且可追溯 |
| 对应真源 | 验收依据来自哪里 | 必须引用 PRD、原型、设计、技术方案或里程碑文档 |
| 验收项 | 逐条列出需要检查的内容 | 每项能判断通过或失败 |
| 证据 | 截图、测试输出、文档链接、人工确认等 | 不允许只有“看起来可以” |
| 结论 | 通过、退回、需讨论、阻塞之一 | 不能使用模糊结论 |
| 问题清单 | 未通过项和风险 | 每个问题有影响和处理建议 |
| 下一步入口 | 通过或失败后去哪里 | 能明确进入下一阶段、退回修复、变更分流或阻塞等待 |

### 6.3 结论口径

- 通过：验收项全部满足，可进入下一阶段。
- 退回：关键验收项未满足，需要回到对应阶段修复。
- 需讨论：存在产品取舍、范围变化或验收口径不清。
- 阻塞：缺少外部输入、环境、权限或关键证据，暂不能继续。

### 6.4 禁止提前写入

验收报告不得写入：

- 未实际验证的通过结论。
- 无证据的人工判断。
- 被验收对象之外的新需求。
- 绕过 Change Request 的范围变化。

## 7. 会签标准

用户会签本文时，需要确认：

- 四类文档契约是否覆盖后续关键真源。
- 每类契约是否明确了必填字段和合格标准。
- 禁止提前写入的内容是否足以防止阶段偷跑。
- 验收报告格式是否能支撑“通过 / 退回 / 需讨论 / 阻塞”门禁。
- 本文是否可以作为后续 S3、S4、P3 和验收阶段的格式真源。

## 8. P2.1 结论

P2.1 建议冻结为：

> 后续所有关键真源文档必须先满足本文定义的格式契约，再进入内容会签。字段不完整、上游真源缺失、提前写入后续阶段内容或缺少验收口径时，文档不得被标记为已会签。
