# NextStep 原始需求真源

状态：已记录，待用户最终会签  
记录日期：2026-07-07  
项目名称：NextStep  
仓库：`https://github.com/linggougou/NextStep.git`

## 1. 原始痛点

用户在和 AI 沟通时，经常出现以下问题：

- 用户脑中有想法，但表达时容易丢失细节。
- 用户考虑不全面，导致 AI 理解跑偏。
- Agent 执行结果不符合预期后，需要反复修改提示词。
- 当前工作流常变成 Agent A 生成提示词，Agent B 执行，结果不满意后再回到 Agent A 修改提示词。
- Prompt 越来越长，但项目依然可能跑偏，因为根因不是提示词写得不够好，而是需求、阶段、闭环和验收没有被硬性管理。

## 2. 关键认知

NextStep 不应被定义为 Prompt 工具，也不应只解决“如何写一段更好的提示词”。

真正要解决的是：

> 用户如何把一个模糊想法，整合成完整项目，再拆成多个可量化、可执行、可验收的小闭环，并持续推进直到全部交付。

## 3. 产品定位

NextStep 是一个面向个人和小团队的 AI 项目闭环落地系统。

它负责：

- 在用户只有模糊概念时，协助用户完善项目需求。
- 在项目开始前，整合并冻结完整项目真源。
- 明确第一版要落地什么，但不把 MVP 当成完整路线的终点。
- 把完整项目拆成多个可量化、可闭环的小模块。
- 为每个模块定义硬性指标、输入、输出、非目标和验收方式。
- 在需求、开发、验收和变更过程中防止项目漂移。
- 让用户持续知道当前项目节点、下一步和是否允许进入下一阶段。

## 4. 产品必须解决的问题

### 4.1 模糊需求无法落地

用户的原始表达通常只是入口需求，不是完整项目需求。

NextStep 必须先把原始需求整合成完整项目结构，再允许进入版本规划或执行。

### 4.2 第一版边界不清

如果一开始没有定义第一版要落地什么，项目就无法形成闭环。

NextStep 必须明确：

- 当前版本解决什么核心问题。
- 当前版本包含什么。
- 当前版本不包含什么。
- 当前版本完成后用户能得到什么。
- 当前版本的硬性验收标准是什么。

### 4.3 缺少闭环硬指标

如果没有硬性指标，Agent 会持续开发、顺手优化、不断扩展，最终导致项目漂移。

NextStep 必须为每个阶段、版本和模块定义可验证指标。

### 4.4 MVP 不是完整落地路径

AI 常见误区是每次讨论都能说清楚一个 MVP，但缺少从 MVP 到完整项目落地的路径。

NextStep 必须先建立完整项目蓝图，再切分版本路线、大里程碑和小里程碑闭环。MVP 只是完整路线中的第一个可交付版本，不是项目规划的终点。

## 5. 核心流程

```text
原始需求
↓
意图理解
↓
需求补全与讨论
↓
需求记录与冻结
↓
产品经理视角整合
↓
完整项目蓝图
↓
产品定义 / PRD
↓
产品原型
↓
用户原型会签
↓
UI 设计效果图
↓
设计真源会签
↓
技术选型与架构
↓
版本路线
↓
大里程碑
↓
小里程碑闭环
↓
执行任务包
↓
开发 / 执行
↓
小里程碑测试验收
↓
合入大里程碑
↓
大里程碑集成验收
↓
UI 还原验收
↓
产品定义验收
↓
交付验收
↓
交付归档
```

变更管理不是单独的末尾步骤，而是贯穿从需求讨论到交付归档的全流程。任何新需求、漏项、范围变化、设计变化、技术风险或验收失败，都必须进入变更分流，不能直接污染当前闭环。

## 6. 核心对象

### 6.1 Project

项目级真源，记录项目为什么存在、解决谁的问题、完整范围是什么。

必须包含：

- 项目目标
- 目标用户
- 核心场景
- 完整需求
- 版本边界
- 非目标
- 成功指标
- 风险
- 变更记录

### 6.2 Version

版本级闭环，记录某一版本要交付什么价值。

必须包含：

- 版本目标
- 版本范围
- 版本非目标
- 可交付成果
- 验收标准
- 回滚或延期规则

### 6.3 Module

可执行、可验收的小闭环。

模块拆解不能只按技术拆，而要按业务闭环拆。

每个模块必须包含：

- 解决的问题
- 输入
- 输出
- 执行任务包
- Definition of Done
- 验收方式
- 明确非目标
- 失败处理入口

### 6.4 Stage

项目阶段和门禁。

每个阶段必须明确：

- 当前阶段名称
- 阶段目标
- 阶段出口
- 不得提前进入的下一阶段
- 允许进入下一阶段的条件

### 6.5 Deliverable

交付物和证据。

包括但不限于：

- 产品定义 / PRD
- 版本路线图
- 小里程碑闭环清单
- 执行任务包
- 验收报告
- 变更记录
- 交付清单

### 6.6 Prototype

产品原型真源，用于让用户在开发前确认产品结构、页面关系、核心流程和关键交互。

必须包含：

- 页面清单
- 主流程
- 关键交互
- 不可偏离项
- 用户会签结论

### 6.7 Design Source

UI 设计真源，用于后续 UI 还原验收。

必须包含：

- 设计稿或高保真效果图
- 视觉规范
- 组件状态
- 响应式要求
- UI 验收标准

### 6.8 Technical Plan

技术选型与架构真源，用于约束开发落地。

必须包含：

- 技术栈
- 架构方案
- 数据模型
- 关键依赖
- 风险与回滚方案

### 6.9 Milestone

项目推进闭环，分为大里程碑和小里程碑。

大里程碑必须能交付一组完整能力，小里程碑必须是可开发、可测试、可验收的最小落地单元。

每个里程碑必须包含：

- 目标
- 范围
- 依赖
- DoD
- 测试方式
- 合入条件
- 验收人或验收标准

## 7. 三把核心锁

### 7.1 需求锁

需求未整合成完整项目真源前，不允许进入开发。

必须确认：

- 项目目标
- 目标用户
- 核心场景
- 完整范围
- 第一版范围
- 非目标
- 验收标准

### 7.2 版本锁

版本边界未确定前，不允许拆模块或执行开发。

新需求不能直接插入当前版本，必须进入变更分流。

### 7.3 闭环锁

模块没有硬性验收指标前，不允许执行。

验收未通过前，不允许进入下一阶段。

## 8. 产品硬规则

- 原始需求必须先整合成完整项目结构。
- 需求讨论完成后，必须先记录和冻结当前需求真源。
- 产品经理视角的产品定义必须先于原型、UI、技术选型和开发。
- 产品原型必须经用户会签后，才能进入 UI 设计。
- UI 设计效果图必须形成设计真源，后续大里程碑完成后要做 UI 还原验收。
- 技术选型与架构必须在开发前完成，不能边开发边默认选型。
- 完整项目必须先拆成版本路线，再拆成大里程碑和小里程碑。
- 每个小里程碑必须有输入、输出、DoD、测试方式、验收方式和非目标。
- Agent 每次执行必须绑定当前小里程碑闭环。
- 小里程碑测试通过后，才能合入对应大里程碑。
- 大里程碑完成后，必须先做集成验收，再做 UI 还原验收和产品定义验收。
- 新需求、漏项、二期需求必须进入变更分流。
- 未通过阶段门禁，不允许进入下一阶段。
- 未经用户确认，不允许改变产品定位、版本范围、验收指标或闭环边界。

## 9. 当前明确非目标

NextStep 当前不做：

- 单纯 Prompt 优化器。
- Agent 市场。
- 多 Agent 编排平台。
- 大而全知识库系统。
- 传统团队项目管理软件。
- 只会生成一次性 MVP 的工具。
- 无门禁、无验收、无项目真源的聊天助手。

## 10. 成功指标

产品成功不能只看生成内容质量，而应看：

- 用户是否能从模糊想法形成完整项目真源。
- 项目是否能被拆成版本路线。
- 版本是否能被拆成多个可量化闭环模块。
- 每个模块是否有明确验收标准。
- 执行过程中新增需求是否被正确分流。
- 用户是否始终知道当前阶段和下一步。
- 项目是否最终完成交付闭环。

## 11. 当前结论

NextStep 的第一条铁律：

> 任何用户原始需求，都必须先被整合成完整项目结构，才能进入版本规划和执行。

NextStep 的完整定位：

> NextStep 是一个 AI 项目闭环落地系统。它帮助用户把模糊想法整合成完整项目真源，再拆成版本路线和多个可量化、可执行、可验收的小闭环，并通过阶段门禁、执行任务包、验收指标和变更管理，推动项目从需求、开发到验收交付持续落地。
