# NextStep 能力地图

状态：P1 已会签
记录日期：2026-07-07
上游真源：`docs/product-specs/002-complete-project-blueprint.md`

## 1. 能力分层

NextStep 的能力按 5 层组织。

| 层级 | 作用 | 包含能力 |
|---|---|---|
| 需求真源层 | 接住、补全并冻结用户需求 | 需求入口、需求补全、需求冻结 |
| 产品设计层 | 把需求转成产品定义和设计真源 | 产品定义、产品原型、UI 设计真源 |
| 技术规划层 | 把产品方案转成可实现方案 | 技术选型、架构、风险与回滚 |
| 里程碑闭环层 | 把项目拆成可交付路径 | 版本规划、大里程碑、小里程碑、阶段门禁 |
| 执行交付层 | 控制执行、验收、变更和归档 | 执行任务包、测试验收、UI 验收、产品验收、变更分流、交付归档 |

## 2. 能力清单

### 2.1 需求入口

目的：接住用户的模糊表达，识别表层需求和深层问题。

输入：

- 用户自然语言描述。
- 可选背景材料。

输出：

- 原始需求记录。
- 意图理解摘要。
- 关键缺口。
- 下一步澄清建议。

硬性指标：

- 必须识别目标、场景、约束、输出和非目标缺口。
- 不能直接生成开发任务。

### 2.2 需求补全与冻结

目的：通过 AI 与用户讨论，把模糊需求补全，并记录为需求真源。

输入：

- 原始需求记录。
- 用户补充信息。

输出：

- 需求清单。
- 待确认项。
- 已拒绝或后置需求。

硬性指标：

- 用户确认当前需求被完整记录。
- 需求未冻结时，不允许进入产品定义。

### 2.3 产品定义

目的：站在产品经理视角，把需求整合成产品定义，而不是直接进入开发。

输入：

- 需求清单。

输出：

- 产品定义 / PRD。
- 项目目标。
- 目标用户。
- 核心场景。
- 项目范围。
- 非目标。
- 成功指标。

硬性指标：

- 产品定义不完整时，不允许进入原型。
- 用户必须确认当前项目定义。

### 2.4 产品原型

目的：在 UI 和开发前，让用户确认产品结构、页面流程和关键交互。

输入：

- 产品定义。

输出：

- 页面清单。
- 主流程。
- 关键交互。
- 原型会签记录。

硬性指标：

- 原型未会签，不允许进入 UI 设计。
- 原型必须标注不可偏离项。

### 2.5 UI 设计真源

目的：形成后续 UI 还原验收依据。

输入：

- 已会签原型。

输出：

- UI 设计效果图。
- 设计规范。
- 组件状态。
- UI 验收标准。

硬性指标：

- 设计真源未确认，不允许进入工程实现。
- UI 验收标准必须可检查。

### 2.6 技术选型与架构

目的：在开发前明确技术路线、架构、风险和回滚方式。

输入：

- 产品定义。
- 已会签原型。
- UI 设计真源。

输出：

- 技术栈。
- 架构方案。
- 数据模型。
- 风险与回滚方案。

硬性指标：

- 技术路线和关键风险可验证。
- 未完成技术方案，不允许进入里程碑实施。

### 2.7 真源管理

目的：维护项目事实，避免聊天记录替代项目真源。

输入：

- 已确认决策。
- 阶段产物。
- 验收结论。

输出：

- 当前项目真源。
- 决策历史。
- 阶段状态。
- 变更记录。

硬性指标：

- 一个事实只能有一个当前真源。
- 任何执行任务必须引用当前真源。

### 2.8 版本规划

目的：把完整项目拆成多个可交付版本。

输入：

- 产品定义 / PRD。

输出：

- V1 范围。
- V2 范围。
- Backlog。
- 每个版本的交付物和验收标准。

硬性指标：

- V1 必须有独立交付价值。
- 后续版本不得污染当前版本。
- 每个版本必须有明确非目标。

### 2.9 大里程碑规划

目的：把版本拆成一组可集成验收的大里程碑。

输入：

- 版本路线。

输出：

- 大里程碑计划。
- 大里程碑交付物。
- 大里程碑验收标准。

硬性指标：

- 每个大里程碑必须有完整能力边界。
- 大里程碑完成后必须经过集成验收、UI 验收和产品验收。

### 2.10 小里程碑拆解

目的：把版本拆成可量化、可执行、可验收的小闭环。

输入：

- 大里程碑计划。

输出：

- 小里程碑清单。
- 小里程碑依赖关系。
- 小里程碑 DoD。
- 小里程碑测试方式。
- 小里程碑验收方式。

硬性指标：

- 小里程碑按业务闭环拆，不按纯技术层拆。
- 每个小里程碑必须有输入、输出、DoD、测试方式、非目标和失败处理入口。

### 2.11 阶段门禁

目的：阻止项目在未达标时进入下一阶段。

输入：

- 当前阶段状态。
- 当前阶段交付物。
- 验收标准。

输出：

- 通过。
- 退回。
- 需讨论。
- 阻塞。

硬性指标：

- 未通过不得进入下一阶段。
- 门禁结论必须可追溯。

### 2.12 执行任务包

目的：让执行 Agent 明确知道当前只做什么。

输入：

- 当前小里程碑闭环。
- 当前项目真源。
- 当前版本边界。

输出：

- 执行背景。
- 任务目标。
- 输入材料。
- 输出格式。
- 非目标。
- 验收标准。
- 失败处理规则。

硬性指标：

- 没有小里程碑闭环不得生成执行任务包。
- 执行任务包不能改变项目真源。

### 2.13 测试与合入验收

目的：判断小里程碑是否可以合入大里程碑。

输入：

- 执行结果。
- 小里程碑 DoD。
- 验收标准。

输出：

- 小里程碑验收报告。
- 问题清单。
- 修复入口。
- 阶段门禁结论。

硬性指标：

- 验收结论只能是通过、退回、延期、变更、阻塞。
- 未验证不得包装为完成。
- 小里程碑测试通过后，才能合入大里程碑。

### 2.14 UI 与产品验收

目的：判断大里程碑是否符合设计效果图和产品定义。

输入：

- 大里程碑集成结果。
- UI 设计真源。
- 产品定义。

输出：

- UI 还原验收报告。
- 产品定义验收报告。
- 大里程碑通过或退回结论。

硬性指标：

- UI 验收必须对照设计真源。
- 产品验收必须对照 PRD / 产品定义。
- 两类验收未通过，不允许进入交付。

### 2.15 变更分流

目的：防止新需求偷渡进当前闭环。

输入：

- 新需求。
- 漏项。
- 执行中发现的问题。

输出：

- 当前阶段缺口。
- 当前阶段增强项。
- 后续版本需求。
- Backlog。
- 拒绝。
- 高风险路线变更。

硬性指标：

- 影响路线、版本边界或验收门禁的变更必须用户确认。
- 变更结论必须写入真源。

### 2.16 交付归档

目的：让项目成果、证据和风险可追溯。

输入：

- 已通过验收的交付物。
- 阶段报告。
- 风险和延期项。

输出：

- 交付清单。
- 归档记录。
- 后续版本入口。

硬性指标：

- 交付前必须有验收结论。
- 交付后新增需求必须进入后续版本或变更管理。

## 3. 能力优先级

| 优先级 | 能力 | 原因 |
|---|---|---|
| A0 | 需求补全与冻结、产品定义、真源管理、阶段门禁 | 决定 NextStep 是否能把原始需求变成完整项目 |
| A1 | 产品原型、UI 设计真源、技术选型与架构 | 决定项目是否能按真实开发流程进入落地 |
| A2 | 版本规划、大里程碑、小里程碑、执行任务包、测试与合入验收 | 决定项目是否能持续推进 |
| A3 | UI 与产品验收、变更分流、交付归档、外部 Agent 连接 | 决定长期项目是否可维护 |
| A4 | 多人协作、Agent 市场、知识库扩展 | 属于后续扩展，不进入当前核心闭环 |

## 4. 能力边界

NextStep 可以生成执行任务包，但不等同于执行 Agent。

NextStep 可以管理项目状态，但不等同于传统项目管理软件。

NextStep 可以使用 AI 分析需求，但不等同于聊天助手。

NextStep 可以输出提示词，但提示词只是执行任务包的一部分。

## 5. 后续阶段输入

本能力地图通过后，P2 先进入产品原型、设计真源与技术前置；P3 再把能力拆成版本路线、大里程碑和小里程碑闭环。

P2 至少需要输出：

- 产品原型。
- 用户原型会签标准。
- UI 设计真源输入要求。
- 技术前置清单。
- 技术风险和后续验证问题。

P3 至少需要输出：

- V1/V2/V3/Backlog 路线。
- 大里程碑计划。
- 小里程碑闭环清单。
- 每个小里程碑的输入、输出、DoD、测试方式、验收方式。
- 验收矩阵。
- 小里程碑依赖关系。
