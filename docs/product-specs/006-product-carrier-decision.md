## 1. 文档目标

本文用于裁决 NextStep 的主交互载体、真源承载方式、辅助入口和后续集成面。

本文确认的不只是“用户从哪里进入”，还包括：

- 正式项目事实承载在哪里。
- 哪些动作可以由 AI 自动建议。
- 哪些动作必须由用户显式确认。
- Web 是否进入当前主路线，还是仅保留为后续候选分支。

## 2. 明确非目标

本文不做以下内容：

- 不输出高保真 UI 设计稿。
- 不冻结技术栈、数据库、部署平台或模型供应商。
- 不定义具体 Skill 参数、MCP 协议字段或 API 结构。
- 不冻结版本路线、大里程碑或小里程碑。
- 不生成执行任务包。
- 不生成验收结论或交付报告。

## 3. 本次裁决拆成两层

本次不再把“主载体”与“真源承载方式”混为一谈。

NextStep 需要分别裁决：

| 层级 | 要回答的问题 |
|---|---|
| 主交互载体 | 用户平时主要通过什么方式驱动 NextStep 工作 |
| 真源承载方式 | 哪些正式项目事实必须沉淀到结构化真源，而不是只停留在聊天里 |
| 辅助入口 | 是否存在辅助但非主路线的交互形态 |
| 集成面 | 是否需要供外部 Agent 或工具调用的能力出口 |

## 4. 裁决结果

| 维度 | 结论 |
|---|---|
| 主交互载体 | `Skill / 聊天入口` |
| 真源承载方式 | `项目文档真源 + PROJECT_ROUTE_LOCK.md + 对应阶段真源文档` |
| 当前辅助入口 | 当前不单独建立新的 Web 工作台或 App 主入口 |
| 后续集成面 | `MCP 服务 / API` |
| 当前不进入主路线 | `Web 项目驾驶舱`、`纯 App`、`纯 MCP`、`纯无 UI / Headless`、`只有聊天记录没有文档真源的纯 Skill` |

一句话结论：

> NextStep 当前采用 `Skill 主载体 + 文档真源承载 + Web 暂不进入主路线` 的方案推进。

## 5. 为什么不选 Web 项目驾驶舱作为当前主路线

本次会签后的判断是：

- NextStep 的核心价值是把模糊需求稳稳推进到可交付，而不是把项目状态展示成一个更完整的看板。
- 如果当前把 `Web 项目驾驶舱` 作为主载体，产品重心会过早偏向“状态展示层”，而不是“需求推进与阶段门禁层”。
- Web 工作台并非完全无价值，但在当前阶段属于偏重实现，会分散对 Skill 主流程、会签节点和真源回写规则的定义精力。
- 真正不可丢的是“结构化真源”和“门禁约束”，这些并不要求一开始就先建设一个完整 Web 主界面。

因此，`Web` 当前不进入主路线，但保留为后续候选分支，而不是被永久否定。

## 6. 为什么也不选“纯 Skill、只有聊天记录”

本次并没有把 NextStep 定义成一个“只有对话、不需要文档”的 Skill。

原因是：

- 聊天内容天然易漂移，不适合承担正式会签、阶段门禁和交付物归档。
- 如果没有结构化真源，用户很难稳定知道“当前在哪个阶段、哪些已确认、哪些不能改、下一步是什么”。
- 多轮对话、跨项目切换、后续 Agent 执行和验收都需要明确引用依据，不能只依赖聊天上下文。

因此，本次选中的不是“纯 Skill”，而是：

> `Skill 负责推进，文档真源负责冻结事实。`

## 7. 选定方案的模拟使用手册

### 7.1 入口与触发方式

| 项目 | 说明 |
|---|---|
| 主入口 | 用户在支持 Skill 的 Agent 或聊天环境中调用 NextStep |
| 默认触发方式 | 不默认静默执行 |
| 推荐触发方式 | 用户显式调用，或系统建议进入 NextStep 流程后由用户确认 |
| 为什么不默认自动执行 | 载体裁决、需求冻结、会签和变更分流都涉及正式项目事实，不适合无感触发 |

### 7.2 用户主路径

1. 用户在对话里提出一个目标、需求或变更。
2. 用户显式调用 NextStep Skill，或接受系统给出的“建议进入 NextStep 流程”提示。
3. Skill 先识别当前项目、当前阶段和关键缺口，再决定是继续推进、补真源、会签还是变更分流。
4. Skill 在对话中给出结构化建议，而不是只追问。
5. 涉及正式确认的节点，由用户显式确认。
6. 确认后的事实回写到对应文档真源，而不是只留在聊天里。
7. 后续技术架构、版本拆解、执行任务包和验收，都继续引用这些文档真源。

### 7.3 Skill 主要负责什么

| 能力 | 使用方式 |
|---|---|
| 需求补全 | 在对话中追问目标、场景、约束、非目标，并整理成结构化草案 |
| 当前阶段判断 | 读取路线锁与当前真源，判断用户现在处于哪个阶段 |
| 门禁缺口提示 | 告诉用户为什么当前不能进入下一阶段 |
| 会签前总结 | 把待确认内容整理成短结论，供用户判断 |
| 变更分流建议 | 识别新需求、漏项和范围变化，给出分类建议 |
| 真源回写建议 | 明确这次确认会写入哪份文档 |

### 7.4 文档真源承载什么

| 真源位置 | 承载内容 |
|---|---|
| `docs/product-specs/001-original-requirement.md` | 原始需求与早期意图记录 |
| `docs/product-specs/002-complete-project-blueprint.md` | 完整项目蓝图与阶段总流程 |
| `docs/product-specs/003-user-journey.md` | 用户旅程与阶段链路 |
| `docs/product-specs/004-capability-map.md` | 能力边界与输入输出关系 |
| `docs/product-specs/006-product-carrier-decision.md` | 主交互载体、真源承载方式与候选分支定位 |
| `docs/design-docs/s3-skill-interaction-source.md` | Skill 主载体下的交互规则、回写真源规则和确认节点 |
| 对应 Change Request 真源 | 新需求、漏项和范围变化的分流记录 |

原则是：

- Skill 不等于真源。
- 聊天摘要不等于会签记录。
- 用户确认后的正式事实必须落盘。

### 7.5 自动动作与显式确认边界

| 可以自动完成的动作 | 必须用户显式确认的动作 |
|---|---|
| 识别当前阶段、识别缺口、整理候选方案、生成文档草案、给出变更分流建议、提示门禁原因 | 需求冻结、产品定义会签、原型会签、产品载体裁决、变更最终分类、阶段通过 / 退回 / 阻塞结论 |

### 7.6 多项目与上下文规则

- Skill 每次进入正式流程前，必须先明确当前项目是谁。
- 若项目不明确，先要求用户选择或创建项目，不能靠猜测推进。
- 若当前阶段所需真源缺失，Skill 不能继续生成后续阶段内容，而应提示回到正确节点。
- 项目切换后，新的确认结果不能覆盖旧项目真源。

### 7.7 阻塞与异常处理

出现以下情况时，Skill 必须停止推进并明确原因：

- 当前项目未识别。
- 当前路线锁或当前阶段真源缺失。
- 用户想直接跳过原型、载体裁决或技术架构。
- 新需求正在污染当前闭环但尚未分流。
- 当前确认会覆盖已会签真源，但尚未进入正式变更流程。
