## 1. 文件定位

本文不是最终技术方案，不选择技术栈，也不冻结架构。

本文只为后续 S4 技术架构阶段准备输入，明确 NextStep 需要被技术方案接住的产品对象、系统能力、关键风险、验证问题和回滚关注点。

## 2. 技术方案必须服务的产品原则

后续技术架构必须服务以下原则：

- 项目真源先于执行。
- 阶段门禁先于阶段切换。
- 需求、版本、小里程碑和交付物必须可追溯。
- 新需求必须进入变更分流。
- 执行任务包不能改变项目真源。
- 未通过验收不得包装为完成。
- 聊天记录不能替代项目状态。

## 3. 核心领域对象

后续架构至少需要评估以下领域对象：

| 对象 | 作用 | 技术关注点 |
|---|---|---|
| Project | 项目级真源 | 生命周期状态、所有权、归档 |
| Requirement Set | 需求记录与冻结 | 版本化、会签、变更追踪 |
| Product Definition | 产品定义 / PRD | 结构化字段、会签状态、引用关系 |
| Prototype | 产品原型 | 页面、流程、交互、不可偏离项 |
| Design Source | UI 设计真源 | 设计稿链接、组件状态、验收标准 |
| Technical Plan | 技术方案 | 技术栈、架构、风险、回滚方案 |
| Version | 版本闭环 | 范围、非目标、验收标准 |
| Major Milestone | 大里程碑 | 集成验收、依赖、小里程碑聚合 |
| Small Milestone | 小里程碑 | 输入、输出、DoD、测试、失败处理 |
| Stage Gate | 阶段门禁 | 通过、退回、需讨论、阻塞 |
| Deliverable | 交付物 | 真源状态、证据、归档 |
| Change Request | 变更分流 | 影响分析、分流结论、用户确认 |
| Execution Packet | 执行任务包 | 范围锁定、输入输出、验收方式 |

## 4. 核心系统能力

后续技术方案至少要覆盖：

- 项目状态管理：维护当前阶段、里程碑、交付物和门禁状态。
- 真源版本管理：区分草稿、待会签、已会签、已归档。
- 阶段门禁引擎：根据 DoD 判断是否允许推进。
- 变更分流：记录新需求、漏项、验收失败和分流结论。
- 交付物中心：管理 PRD、原型、设计、技术方案、验收报告。
- AI 导师交互：把用户表达转成建议、问题、结构化真源。
- 执行任务包生成：后续基于小里程碑生成边界清晰的 Agent 指令。
- 验收记录：保存通过、退回、需讨论、阻塞结论。

## 5. 关键技术决策问题

S4 技术架构阶段必须回答以下问题：

### 5.1 数据与真源

- 真源是否需要事件溯源，还是普通版本记录即可。
- 会签后的真源如何防止被直接覆盖。
- 草稿、已会签、归档状态如何建模。
- 变更请求如何关联受影响的真源。

### 5.2 AI 交互

- AI 导师如何拿到当前项目状态和阶段门禁。
- AI 输出如何被转成可审查的结构化真源。
- 哪些内容允许 AI 自动建议，哪些必须用户确认。
- 如何防止 AI 直接推进未通过阶段。

### 5.3 阶段门禁

- DoD 是写死在代码中，还是由项目真源配置。
- 阶段通过、退回、需讨论、阻塞如何形成审计记录。
- 缺失交付物如何被识别。
- 阶段切换是否需要强制用户确认。

### 5.4 交付物与附件

- 文档交付物存储在哪里。
- 是否需要支持外部设计链接、代码仓库链接、测试报告链接。
- 交付物如何标记来源、状态和版本。
- 后续是否需要导出交付归档包。

### 5.5 执行 Agent 集成

- NextStep 生成执行任务包后，是否直接调用 Agent，还是先让用户复制确认。
- 执行结果如何回填验收。
- Agent 跑偏时如何判断回退节点。
- 初版是否只做任务包生成，不做多 Agent 编排。

## 6. 技术风险清单

| 风险 | 表现 | 后续验证方式 |
|---|---|---|
| 真源不可维护 | 聊天内容和项目状态混在一起 | 建立结构化真源与状态流转验证 |
| 门禁过软 | 用户或 AI 可以绕过阶段 | 建立阶段推进拦截用例 |
| AI 输出不可控 | AI 建议直接污染真源 | 建立用户确认和草稿状态 |
| 数据模型过早复杂 | 初期为所有后续场景建模 | P3 后按版本路线裁剪 |
| 技术栈提前冻结 | P2 直接变成开发方案 | S4 再做候选方案对比和验证 |
| 交付物无证据 | 文档无法追溯来源和状态 | 交付物中心必须记录状态和引用 |

## 7. S4 技术架构输出要求

后续 S4 至少需要产出：

- 技术栈选择与理由。
- 可替代方案和不选原因。
- 数据模型草案。
- 状态机或阶段门禁模型。
- 核心 API 或本地数据契约。
- AI 交互边界。
- 权限和数据安全基本方案。
- 风险验证计划。
- 回滚或迁移方案。

## 8. 当前不冻结的内容

本阶段不冻结：

- 前端框架。
- 后端框架。
- 数据库。
- 部署平台。
- AI 模型供应商。
- Agent 调用方式。
- 认证方案。
- 数据同步方案。

这些内容必须在 S4 技术架构阶段基于 P2 原型和 S3 UI 设计真源判断；若涉及版本路线、大里程碑或小里程碑边界，应留给后续 P3 / S5 里程碑计划裁决。

## 9. P2 结论

P2 技术前置结论是：

> NextStep 的技术方案必须围绕项目真源、阶段门禁、交付物、变更分流和执行任务包构建。技术架构的首要目标不是快速生成一个 MVP，而是确保项目状态、范围、验收和变更可以被长期维护。

用户确认本文后，后续 S4 技术架构阶段可以据此进行技术选型与架构设计。
