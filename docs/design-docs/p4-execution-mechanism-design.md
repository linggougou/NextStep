## 1. 文档定位

本文把已会签 P3 版本/里程碑计划与 S4 技术架构转成 P5 可实现的执行机制设计。它定义逻辑协议、状态、职责、门禁、失败和恢复，不提供产品代码、测试代码、脚本、可执行 Schema 或真实执行任务包。

P4 的完成不代表 NextStep 产品能力已经实现。只有 P5 中可运行的 NextStep 在目标项目 fixture 上通过正例、负例、阻塞、恢复和验收行为验证，才可判定对应 PC 已交付。

## 3. 不可偏离原则

1. 主对话只负责用户沟通、决策和独立任务生命周期协调，不读取或修改项目文件。
2. 集成职责是正式项目状态的唯一写入口，但不得验证、评估或批准自己的候选。
3. 每个执行任务只消费一个冻结任务包，只修改自己的隔离工作区和允许路径。
4. 身份、项目根、正式基线、代际、宿主能力或证据不能证明时默认阻塞。
5. 文档存在、消息返回、任务结束或候选可合并均不等于验收通过。
6. 已会签真源不原地改写；变化必须形成新候选、新代际和新结论。
7. 正式提升只通过 `refs/nextstep/formal` 的 CAS 移动，不覆盖用户当前分支、index 或工作树。
8. 任何正式结论都绑定精确内容摘要和控制身份；内容或身份变化使旧结论失效。
9. Project Provenance Store 和长期 Agent 贡献归因不属于本设计。

## 4. 端到端执行流程

| 步骤 | 责任角色 | 输入 | 输出 / 门禁 | 失败入口 |
|---:|---|---|---|---|
| 1 | 集成任务 | 正式 ref、路线锁、已会签小里程碑 | Project Context、Capability Preflight | 项目解析或宿主预检阻塞 |
| 2 | 集成任务 | 小里程碑、依赖、当前代际 | Execution Packet 候选与校验报告 | 退回 P3/P4 或补输入 |
| 3 | 集成任务 | 已验证任务包 | 持久化任务包、台账和 `dispatch-ready` | Write Transaction 恢复 |
| 4 | 主对话 | `dispatch-ready` | 宿主独立任务与 `dispatch-ack` | 去重恢复或 `manual-isolated` |
| 5 | 执行任务 | 精确任务包、冻结基线 | Immutable Candidate、Result Envelope | 失败/阻塞结果，不改正式状态 |
| 6 | 集成任务 | 结果、最高代际、宿主关联 | 身份分类：有效/重复/stale/conflict | 代际恢复或人工隔离 |
| 7 | 独立验证任务 | Immutable Candidate | 候选验证结论和证据 | 退回执行任务 |
| 8 | 独立评估任务 | 已验证候选、Acceptance Profile | 交互/产品及条件性 UI 结论 | 退回对应能力或证据提供方 |
| 9 | 独立审查任务 | 候选、上游、前序结论 | 独立审查结论 | 退回执行或设计入口 |
| 10 | 集成任务 | 全部适用结论、候选集合 | Final Content Snapshot | 集成冲突或 Write Transaction 恢复 |
| 11 | 独立最终复验任务 | 精确最终快照、预期正式基线 | Verification Credential | 退回集成快照 |
| 12 | 集成任务 + 独立锚验证任务 | 凭证、最终快照 | Audit Anchor、Anchor Proof | 白名单或摘要不一致阻塞 |
| 13 | 集成任务 | 锚、证明、`expected-old` | 正式 ref CAS 提升 | 保持待正式提升并重试/重建 |
| 14 | 主对话/宿主 | 正式 OID、门禁结论 | 用户摘要、任务归档、关闭状态 | 待归档或用户基于证据豁免 |

步骤不得跳过。人工参与只能替代宿主自动创建/确认/归档动作，不能替代候选隔离、独立结论、精确最终复验或 CAS。

| 角色 | 允许 | 禁止 | 关键证据 |
|---|---|---|---|
| 主对话 | 展示摘要、收集确认、创建/继续/归档独立任务 | 读取/写入项目、运行验证、批准阶段 | 用户决定、宿主任务 ID、dispatch ack |
| 集成任务 | 读取真源、生成任务包、维护台账、集成候选、创建快照和执行 CAS | 批准自己的候选、替代独立验收 | 事务、台账、最终快照、正式 OID |
| 执行任务 | 在隔离工作区内按任务包修改和自测 | 扩大路径/目标、移动正式 ref、改变代际 | 候选 OID/树、结果信封、自检证据 |
| 候选验证 | 只读验证精确候选 | 修改候选、做产品取舍 | 验证运行、命令输出、内容摘要 |
| 产品/交互评估 | 按 Profile 判断体验和产品结果 | 声明 Profile 适用性、修改候选 | I/X/P 结论与证据引用 |

| 最终复验 | 只读验证精确 Final Content Snapshot | 接受集成后变化、写项目内凭证 | create-once Verification Credential |

同一任务尝试中，集成角色不能兼任候选验证、产品/交互评估、独立审查、最终复验或锚验证。角色由独立宿主任务 ID 和证据身份区分，不能只靠提示词自称独立。

## 6. 控制身份

所有任务包、控制消息、结果和结论必须绑定同一逻辑控制身份：

```text
repository_id
+ route_generation
+ stage_id
+ plan_id
+ plan_generation
+ task_id
+ task_attempt
+ baseline_oid
```

- `repository_id` 绑定规范项目根和仓库身份，路径字符串不能单独作为身份。
- `route_generation` 在已会签路线变化后推进。
- `plan_generation` 在计划范围、依赖、输入或验收变化后推进。
- `task_attempt` 只在同一任务、同一计划代际内重试时递增。
- `baseline_oid` 必须来自 `refs/nextstep/formal`，不能用活动工作树 `HEAD` 代替。
- 任一字段不一致都不得自动拼接为同一执行链。

任务进入宿主后，以 `dispatch_message_id + host_task_id` 扩展上述控制身份。任务包生成时二者可以为空，但 `dispatch-ack` 持久化后，所有结果、验证和验收结论必须绑定这两个字段。

## 7. Execution Packet 逻辑契约

| 字段组 | 必填字段 | 校验规则 |
|---|---|---|
| Schema | `schema_version`、`packet_id`、`packet_digest` | 版本不支持或摘要不符时拒绝 |
| 控制身份 | 第 6 节全部字段 | 必须与台账、控制信封和正式基线一致 |
| 目标 | `milestone_id`、`objective`、`why_now` | 只能服务一个已会签小里程碑闭环 |
| 输入 | `source_refs[]`、`input_digests[]`、`dependency_proofs[]` | 缺真源、摘要或依赖证明时拒绝 |
| 范围 | `allowed_paths[]`、`forbidden_paths[]`、`non_goals[]` | 路径必须规范化、无重叠、不得越界 |
| 输出 | `required_outputs[]`、`candidate_form` | 输出必须可测试、可验收、可形成不可变候选 |
| 验证 | `checks[]`、`acceptance_types[]`、`failure_rules[]` | 至少包含正例、负例、阻塞和恢复要求 |
| 执行 | `sandbox_mode`、`host_mode`、`timeout_policy` | 必须符合当前 Capability Preflight |
| 上报 | `result_schema_version`、`evidence_requirements[]`、`escalation_rules[]` | 不允许完整上下文或秘密进入结果信封 |
| 有效性 | `created_at`、`expires_at`、`dedup_key` | 过期、旧代际或去重冲突时拒绝 |

任务包生成是产品运行能力，不是把 P3 表格复制成 Markdown。P5 必须证明 NextStep 能根据目标项目真源生成、校验并拒绝任务包。

### 7.1 任务包拒绝条件

- 目标对应多个小里程碑或没有唯一阶段出口。
- 任一必需输入、依赖、基线、路径边界、DoD、验收类型或失败入口缺失。
- 任务要求修改已会签上游，但没有 Change Request。
- Profile 与目标项目已接受路线冲突。
- 宿主模式为 `blocked`，或任务要求的隔离能力高于 `manual-isolated` 可证明能力。
- 任务包摘要与持久化内容不一致，或相同 `dedup_key` 对应不同内容。

## 8. Control Envelope 与派发确认

控制信封只承载控制面最小信息，不承载完整任务上下文。必需字段为 `schema_version`、`message_id`、`message_type`、控制身份、`packet_digest`、`dedup_key`、`created_at`、`expires_at`、`confirmation_required` 和发送方证据。

允许的消息类型：

- `dispatch-ready`：任务包和依赖已持久化，可请求创建独立任务。
- `dispatch-ack`：返回宿主任务 ID、去重键、环境和确认时间。
- `generation-advance`：声明更高计划代际及旧代际失效边界。
- `generation-ack`：确认已持久化新代际。
- `generation-snapshot`：恢复各任务最高有效代际、尝试和墓碑。
- `cancel-tombstone`：使指定旧尝试失效，但不删除历史证据。
- `archive-request` / `archive-result`：正式提升后的项目外幂等归档副作用。

派发顺序必须是“先持久化任务包和 `dispatch-ready`，后创建宿主任务，再持久化 `dispatch-ack`”。创建返回丢失时，使用 `dedup_key + packet_digest + host_task_id` 查询恢复；不得直接再创建一个无法区分的新任务。

## 9. Task Registry Entry 与代际

台账最小字段为：控制身份、任务状态、依赖状态、宿主任务 ID、任务包摘要、候选摘要、结论摘要、最新消息 ID、最高确认代际、墓碑、更新时间和恢复入口。

台账是恢复索引，不是正式产品真源，也不是 Agent 长期贡献库。台账规范状态固定由 `refs/nextstep/control` 指向的不可变控制提交承载；活动进程内存和工作镜像都不是规范状态。

### 9.1 控制 ref、outbox、claim 与 fencing

1. `registry-transition` 从控制 ref 读取旧 OID，生成父提交为旧 OID 的新控制提交，再执行 `old -> new` CAS；失败者丢弃本地候选并重读。
2. 调用宿主副作用前，先以控制 ref CAS 写入 outbox 意图，再以第二次 CAS 取得 `claim_id`、`owner_id`、`lease_expires_at` 和单调递增 `fence_token`。
3. 只有当前最高 fence 的 claim 可以调用宿主；宿主适配必须原子执行 `create-or-return(effect_key, fence_token, payload_digest)`。
4. 旧 fence、同 fence 不同 payload、claim 过期且未被更高 fence 接管或无法恢复原结果时一律拒绝。
5. 宿主副作用成功后，以控制 ref CAS 写入 `dispatch-ack` 并关闭 outbox。副作用后 ack 前崩溃，只能用同一 effect key 恢复原宿主任务。
6. Adapter 或宿主不能原子保证最高 fence 和幂等创建时，禁止 `full`，降为 `manual-isolated`；身份仍不能绑定时为 `blocked`。

控制 ref 非快进、父链断裂、工作镜像摘要不一致或同一 fence 冲突时 fail closed。人工恢复必须保留冲突证据并生成更高代际控制提交。

### 9.2 执行状态机

```text
已准备 -> 待派发 -> 派发待确认 -> 排队中 -> 执行中
-> 待候选验证 -> 待集成 -> 待最终复验 -> 待正式提升
-> 已集成 -> 已归档
```

任一活动状态可进入 `阻塞` 或 `失败`。恢复只能：

- 在身份和正式基线不变时提高 `task_attempt`；
- 在计划或基线变化时提高 `plan_generation`，写入旧代际墓碑并重新生成任务包；
- 在路线变化时提高 `route_generation` 并重新执行 P4/P3 适用门禁。

## 10. Result Envelope 与结果接收

结果信封必需字段：`schema_version`、`result_id`、`result_kind`、控制身份、`dispatch_message_id`、`packet_digest`、`host_task_id`、`outcome`、`gate_conclusion`、`subject_ref`、`subject_digest`、`evidence_refs[]`、`risks[]`、`blocking_reasons[]`、`incomplete_items[]`、`changed_paths[]`、`observed_baseline`、`completed_at` 和 `result_digest`。

- `result_kind` 区分 `execution`、`candidate-verification`、`product-interaction-evaluation`、`independent-review`、`final-verification` 和 `anchor-verification`。
- 执行任务的 `outcome` 只能是 `candidate-ready`、`failed`、`blocked` 或 `cancelled`。
- 验证/评估/审查任务必须填写 `gate_conclusion`，只能是 `通过 / 退回 / 需讨论 / 阻塞`；执行任务不得自填通过结论。
- `subject_ref/subject_digest` 对执行任务绑定候选，对前置结论绑定被判断候选，对最终复验绑定 Final Content Snapshot，对锚验证绑定 Audit Anchor。
- 任何结果都不能直接写 `integrated`、`formally-promoted` 或 `completed-project`；这些状态只由后续门禁和 CAS 产生。

结果分类：

- 低于最高代际：`stale-result`，只归档证据，不进入依赖或集成。
- 同代际、同尝试、摘要相同：幂等重复，复用原记录。
- 同代际、同尝试、身份或摘要不同：`identity-conflict`，阻塞并人工隔离。
- 高于已知代际：未知控制推进，阻塞并请求 `generation-snapshot`。
- 候选缺失、可变、无法绑定基线或越界：退回执行任务。

## 11. 候选与三类前置结论

### 11.1 Immutable Candidate

候选必须绑定父基线、候选提交或树、内容摘要、控制身份和任务包摘要。候选一旦进入验证不可再修改；修复形成新 `task_attempt` 或新 `plan_generation`。

### 11.2 候选验证

候选验证检查任务包 DoD、测试、路径边界、负例和恢复行为。验证环境只读，验证命令或工具产生的文件不得进入候选；若发生污染，当前验证无效。

### 11.3 产品与交互评估

评估使用目标项目 Acceptance Profile。集成验收、交互验收、产品验收分别生成 I/X/P 结论；含 UI 路线额外消费 UI 设计真源和 UI 还原证据。证据缺失产生 `阻塞`，不能降级为 headless。

### 11.4 独立审查

独立审查对照上游真源、任务包、候选摘要、前序结论和风险矩阵给出 PASS/REVISE/REJECT 或项目规定等价结论。审查只决定候选是否可进入集成，不移动正式 ref。

上述三类结论必须分别存证。适用结论未通过时，候选不得进入 Final Content Snapshot。

## 12. 集成与 Write Transaction

集成任务只在隔离暂存区工作。`Write Transaction` 最小字段包括：事务 ID、控制身份、候选集合及顺序、目标清单、允许路径、预期正式基线、before/after 摘要、准备状态、验证状态、快照状态、失败证据和恢复入口。

集成顺序：

1. 从正式 ref 建立隔离暂存基线。
2. 按已会签依赖顺序应用通过门禁的候选。
3. 校验路径白名单、候选摘要、冲突和上游保护。
4. 生成集成后业务/真源树并运行集成验收。
5. 写入轻量台账、检查点和复验前留痕。
6. 冻结 `Final Content Snapshot`，之后禁止继续写入该快照。

任何冲突、越界、摘要变化或依赖缺失都使事务进入 `阻塞`。自动补偿只允许回退本事务能够证明归属的暂存写入，不操作用户活动工作树，不使用破坏性 Git 命令。

## 13. 最终复验、审计锚与正式提升

### 13.1 Final Content Snapshot

最终快照绑定父正式基线、完整树/提交、控制身份、纳入候选、适用门禁、验收结论、风险反扫和快照摘要。快照变化必须重新执行最终复验。

### 13.2 Verification Credential

独立最终复验任务对精确快照执行所有适用验证，并在 S4 冻结的项目外受控证据根 `$CODEX_HOME/nextstep/evidence/<repository-id>/` create-once 写入凭证。凭证绑定 `verification_run_id`、快照摘要、预期正式基线、验证任务身份、结论、证据摘要和时间。

不能提供 no-replace 安装和父目录持久化保证时，凭证能力为不可用，正式提升阻塞。

### 13.3 Audit Anchor 与 Anchor Proof

集成任务从已通过凭证生成审计锚。锚相对最终快照只允许修改本轮 `.codex/operations-log.md`、`.codex/verification-report.md` 和专属 review 路径。独立锚验证任务校验父链、凭证摘要、路径白名单和业务/真源子树不变，并 create-once 生成 Anchor Proof。

### 13.4 正式引用 CAS

集成任务重新校验凭证与 Anchor Proof 后执行：

```text
CAS refs/nextstep/formal: expected-old -> audit-anchor
```

- CAS 成功才生成“正式提升通过”结论。
- 首次初始化 `refs/nextstep/formal` 是唯一允许 `expected-old` 无前驱的例外，且必须绑定用户确认的现有基线；后续提升必须为后代快进。
- CAS 失败保持 `待正式提升`，不得报告已集成或项目完成。
- 正式基线未变化时可重试同一锚；基线变化时必须废弃旧凭证和证明，重建最终快照并复验。
- 提升成功后禁止补写项目内容；通知、同步用户分支和宿主归档是独立幂等副作用。

## 14. Acceptance Profile 与验收报告

### 14.1 Profile 适用性

| 场景 | 必需验收 | UI 证据 | 适用性来源 |
|---|---|---|---|
| NextStep 自身当前路线 | I/X/P | 不要求 | NextStep 已接受的 headless 路线 |
| headless 目标项目 | I/X/P | 不要求 | 目标项目已接受路线 |
| 含 UI 目标项目 | I/X/P + UI 还原验收 | 必需 | 目标项目已接受路线 |
| Profile 与路线冲突 | 拒绝配置并阻塞 | 不消费 | 冲突证据 |

独立验收任务只能提供或采集证据、校验证据引用并记录结论，不能声明项目是否含 UI。UI 设计真源和 UI 还原证据由目标项目或独立验收任务提供；NextStep 只校验和记录。

### 14.2 四态报告

每份验收报告必须包含唯一验收对象、对应真源、逐项验收项、精确内容摘要、证据、`通过 / 退回 / 需讨论 / 阻塞` 结论、问题清单和下一步入口。

- I：候选组合、依赖、接口/文件边界和正式基线一致。
- X：目标用户交互、确认、异常和恢复符合交互真源。
- P：产品目标、范围、非目标和成功阈值满足。
- UI：仅含 UI 目标项目适用，检查设计真源版本和还原证据。

任一适用报告缺失、对象摘要不一致或结论非通过时，不得进入正式提升。

## 15. Final Acceptance 与项目关闭

Final Acceptance 对全部 PC-01..PC-20、V1..V4、TG/S4 风险、I/X/P、适用 UI、范围外和 Backlog 执行反扫。它必须绑定最终正式 OID、全部证据摘要和用户关闭确认。

- `PC-20.FA` 通过后，Final Acceptance 结论不会因后续宿主归档失败而反转。
- 宿主任务归档成功后，项目可以标记完全关闭。
- 宿主归档失败时保持 `待归档`，记录重试证据，不得伪报完全关闭。
- 用户可以基于明确失败证据豁免宿主归档；豁免记录不等于归档成功，也不改变正式 OID 和 FA 结论。

## 16. Capability Preflight 与宿主模式

预检必须分两阶段：

1. `host-bootstrap` 不读取或写入项目，只证明宿主版本、独立任务创建/查询/继续/归档、稳定任务 ID、权限隔离和审批/阻塞回传能力。
2. 只有 `host-bootstrap` 通过后才运行一次性 `project-probe`；它在隔离 fixture 中验证精确 worktree 起点、信封往返、不可变候选、只读验证、确认丢失恢复、最终快照、项目外凭证、锚、CAS 和归档，并证明失败后正式 ref 与业务真源不变。

| 模式 | 进入条件 | 分派方式 | 禁止行为 |
|---|---|---|---|
| `full` | 自动任务生命周期、候选隔离、只读验证、最终复验和 CAS 均可证明 | 计划内自动扁平分派和恢复 | 跳过持久化确认 |
| `manual-isolated` | 自动创建/确认/归档不可靠，但独立身份、候选和验证可绑定 | 请求用户执行最小宿主操作，NextStep 继续校验关联 | 把同任务串行冒充独立任务 |
| `blocked` | 任一核心隔离、身份、最终复验或 CAS 能力不可证明 | 不派发 | 降级继续或伪造支持状态 |

能力证据绑定宿主、版本、项目、权限、检测时间和有效期。任一绑定变化使旧证据失效并重新预检。

## 17. 阻塞、失败与恢复

| 事件 | 保持状态 | 恢复动作 | 不允许 |
|---|---|---|---|
| `dispatch-ack` 丢失 | 派发待确认 | 按去重键查询宿主并补确认 | 盲目重复创建 |
| 迟到旧代际结果 | 原任务不变 | 标记 stale 并归档证据 | 进入依赖或集成 |
| 同代际身份冲突 | 阻塞 | 人工隔离、推进代际 | 后写覆盖 |
| 候选验证失败 | 待候选验证/退回 | 新 attempt 修复并重验 | 原地修改已验证候选 |
| 集成冲突 | 待集成/阻塞 | 回到对应候选或 Change Intake | 修改正式 ref 规避冲突 |

| 凭证 create-once 冲突 | 阻塞 | 逐字节校验；不一致视为篡改 | 覆盖目标文件 |

| 宿主归档失败 | 待归档 | 幂等重试或用户证据豁免 | 反转 FA 或伪报归档成功 |

## 18. Change Intake

所有执行中发现的新需求、漏项、范围变化或上游冲突必须形成 Change Intake，字段至少包括来源、描述、受影响真源/PC/里程碑、当前正式基线、风险、验证成本、建议分流、用户决定和新代际影响。

分流只能是：

- `当前阶段缺口`：不修复无法满足当前 DoD，回到当前阶段并推进计划代际。
- `当前阶段增强项`：不影响当前出口，进入经确认的 Backlog，不打断执行。
- `高风险基础变更`：影响产品、交互、架构、正式提升或安全边界，建立正式 Change Request 并阻塞相关任务。
- `后续阶段需求`：进入后续版本/阶段里程碑。
- `想法型需求`：记录候选，不进入执行。
- `拒绝`：记录原因，不生成任务包。

任何分流改变已会签任务包输入、范围、DoD 或验收时，旧代际必须墓碑失效并重新生成任务包。

## 21. 权限、证据保留与逻辑工具边界

### 21.1 数据最小化与写入检查

- 禁止保存完整对话、内部推理、密钥、Token、未脱敏环境变量、无关偏好、无关项目内容和大段原始日志。

- 所有写入前执行字段白名单、路径白名单、大小限制和 secret/PII 扫描。疑似秘密阻塞写入；秘密已进入 Git 时停止正式提升并进入吊销/清理流程。

### 21.2 证据保留

- 当前或历史正式 ref 可达审计锚引用的 Verification Credential 和 Anchor Proof 不得自动删除。

- 清理失败不修改正式引用或验收结论，只标记待人工清理。
- 凭证目录不可用时最终复验保持 `blocked`，不得把证据降级到聊天或临时 stdout。
