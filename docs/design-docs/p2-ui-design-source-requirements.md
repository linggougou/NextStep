## 1. 文件定位

本文不是 UI 高保真设计稿，也不是最终设计规范。

本文只定义在未来恢复 `Web / UI` 候选分支时，后续 `S3 UI 设计真源` 必须接住哪些输入、产出哪些证据、满足哪些验收条件，避免 UI 设计阶段脱离产品原型。

## 2. UI 设计阶段必须基于的输入

若后续恢复 `Web / UI` 候选分支，UI 设计真源必须基于以下已确认内容：

- 产品定位：AI 项目闭环落地系统。
- 产品形态假设：项目驾驶舱优先，聊天辅助；当前仅为 `Web / UI` 候选分支假设。
- 核心页面：见 `docs/design-docs/p2-product-prototype.md` 第 4 节。
- 主流程：从模糊想法到需求冻结、产品定义、原型会签、门禁推进和变更分流。
- 不可偏离项：见 `docs/design-docs/p2-product-prototype.md` 第 9 节。
- 阶段门禁：通过、退回、需讨论、阻塞四类结论。

## 3. UI 设计真源必须覆盖的页面

| 页面 | 设计重点 | 必须表达的状态 |
|---|---|---|
| 项目列表 | 多项目状态一眼可判断 | 进行中、阻塞、待会签、已交付 |
| 项目创建 / 需求入口 | 降低用户表达压力 | 空状态、已识别缺口、推荐补全 |
| 需求工作台 | 让需求补全和冻结可见 | 待确认、已确认、被拒绝、后置 |
| 产品定义 | 让产品经理视角结构化 | 目标、用户、范围、非目标、指标 |
| 项目驾驶舱 | 让当前阶段和下一步成为视觉中心 | 当前阶段、缺口、风险、推荐行动 |
| 产品原型会签 | 让用户确认页面和流程 | 待会签、通过、退回、需讨论 |
| 阶段门禁 | 强化硬性判断 | 通过、退回、需讨论、阻塞 |
| 交付物中心 | 区分真源、草稿和证据 | 草稿、待会签、已会签、已归档 |
| 变更分流 | 防止新需求偷渡 | 当前缺口、后续阶段、Backlog、拒绝 |

## 4. 设计必须表达的核心信息

### 4.1 当前在哪

用户必须能在 5 秒内判断：

- 当前项目。
- 当前生命周期阶段。
- 当前阶段状态。
- 当前阶段缺口。
- 是否允许进入下一阶段。

### 4.2 下一步是什么

每个关键页面都必须有明确下一步行动，但行动不能绕过门禁。

下一步行动示例：

- 补全需求缺口。
- 会签当前需求真源。
- 查看当前阶段 DoD。
- 处理阻塞变更。
- 生成下一阶段输入。

### 4.3 什么不能做

UI 不应只显示可点击动作，也要显示被锁住的动作和原因。

示例：

```text
暂不能进入开发
原因：尚未完成 UI 设计真源和技术架构。
下一步：先确认是否重新进入 `Web / UI` 候选分支；若进入，再完成对应 UI 设计真源。
```

## 5. 组件状态要求

后续设计稿至少需要覆盖以下组件状态：

| 组件 | 状态 |
|---|---|
| 阶段状态卡 | 未开始、进行中、待会签、门禁通过、退回、阻塞 |
| 交付物卡片 | 缺失、草稿、待会签、已会签、已归档 |
| 下一步行动 | 可执行、被锁定、需用户确认、需变更分流 |
| 风险提示 | 信息、警告、阻塞、路线变更 |
| 会签按钮 | 待确认、已确认、退回修改 |
| 变更项 | 当前阶段缺口、增强项、后续阶段、Backlog、拒绝 |
| AI 建议块 | 推荐、原因、需要用户确认的取舍 |

## 6. 信息密度要求

NextStep 不是轻量聊天工具，必须承载项目状态和门禁信息。UI 设计应避免两种极端：

- 信息太少：用户只看到聊天框，不知道项目状态。
- 信息太满：用户被大量文档和指标压住，不知道下一步。

推荐设计重心：

- 首页突出一个主状态：当前阶段和下一步。
- 次级区域展示交付物、风险和变更。
- 深层详情通过抽屉、详情页或折叠区域承载。

## 7. 响应式要求

后续 UI 设计真源至少覆盖：

- 桌面端：项目驾驶舱、工作台和交付物管理为主。
- 平板端：保持状态卡和下一步行动优先。
- 移动端：优先查看项目状态、处理会签和变更提醒，不强求复杂文档编辑。

移动端不得把所有信息压缩成单一聊天流。

## 8. UI 验收标准输入

后续 S3 必须产出可用于 UI 还原验收的标准，包括：

- 页面级验收清单。
- 组件状态验收清单。
- 响应式断点要求。
- 空状态、错误状态、阻塞状态示例。
- 关键文案和语气规范。
- 设计不可偏离项。

## 9. 设计真源会签标准

UI 设计真源完成后，用户至少需要确认：

- 是否仍然体现项目驾驶舱优先，而不是聊天优先。
- 是否清楚表达“当前在哪、下一步是什么、什么不能做”。
- 是否覆盖所有核心页面和组件状态。
- 是否能支撑后续 UI 还原验收。
- 是否没有绕过产品原型中的不可偏离项。

## 10. P2 结论

P2 对 UI 的约束是：

> 若未来恢复 `Web / UI` 候选分支，UI 设计应把 NextStep 设计成项目状态优先的项目驾驶舱。设计稿不仅要好看，更要让阶段、门禁、交付物、风险、下一步和变更分流一眼可见，并形成可用于后续 UI 还原验收的设计真源。
