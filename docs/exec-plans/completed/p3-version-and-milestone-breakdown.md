## 5. Definition of Done

- 完整项目必需能力先于版本切分冻结，每项都进入某个连续实施版本或 `Final Acceptance`，不存在未分配核心能力。
- V1 有独立工程交付价值且范围小于完整项目；V2、V3 及后续版本连续承接剩余必需能力，直到完整项目交付。
- 每个中间版本都明确包含项、非目标、进入条件和退出门禁，但其通过不得被表述为整个项目完成。
- 当前版本通过门禁后，默认进入下一版本的准备和启动流程；仍必须遵守阶段门禁、验证结论、用户会签和变更分流。
- `Final Acceptance` 对完整项目而非单个版本执行，全部必需能力和全链路验收通过后才能宣告项目完成。
- Backlog 只承载不影响完整项目完成的可选增强或经变更分流明确后置的事项；范围外项单独记录，不进入连续版本链或 Backlog。
- P1 蓝图中的 V1/V2/V3/Backlog 示例已重新审视，没有直接当作既定路线冻结。
- 每个大里程碑有不重叠的目标、范围、交付物、通过条件和失败条件。
- 每个小里程碑都有明确输入、输出、DoD、测试方式、非目标、依赖和失败退回入口。
- 每个小里程碑形成可独立验证的最小闭环，并服务所属大里程碑的集成验收。
- 成功指标具备量化口径、阈值、样例、证据来源和失败判定。
- 验收矩阵覆盖版本、大里程碑、小里程碑、交互验收、产品验收及条件性 UI 还原验收。
- 能力预检、候选验证、最终复验、审计锚和正式引用 CAS 被安排到适当里程碑，但不在 P3 编写实现代码。
- Project Provenance Store、长期 Agent 贡献归因和 Web/UI 候选分支未进入当前路线。
- P3 候选通过独立规划审查并由用户会签。

## 6. 明确非目标

- 不编写产品实现代码、测试代码或脚本。
- 不生成真实执行任务包，不开始小里程碑实施。
- 不提前设计 P4 的最终执行协议、API、Schema 或目录物理拆分。
- 不改变已会签 S4 技术架构；需要改变时先进入 Change Request。
- 不恢复 Web/UI 候选分支。
- 不把 Project Provenance Store 或长期 Agent 贡献溯源放入任何实施版本、Final Acceptance 或 Backlog。
- 不以“先做 MVP”为由删除完整项目路线或已确认验收门禁。

## 7. 完整项目完成定义

NextStep 只有同时满足以下条件，才允许判定整个项目完成：

1. 用户可以从模糊想法建立、补全、冻结并恢复需求真源。
2. 产品定义、原型、载体裁决、Skill 交互真源和技术架构均可按门禁形成并会签。
3. 完整项目可以拆成连续实施版本、大里程碑和可执行的小里程碑，并保持全量需求覆盖。
4. 每个小里程碑都能生成边界明确、可验证、可退回的执行任务包。
5. 主对话保持唯一用户入口、默认安静并只负责沟通、决策和扁平分派，后台过程不污染其上下文；至少一个正式支持的主宿主可以在 `full` 模式下自动分派和恢复。
6. 开发、文档、测试、评估、审查、验证、恢复和集成由职责隔离的任务完成，不能自我批准。
7. 候选验证、产品与交互评估、独立审查、精确最终集成复验和正式提升五类结论均可独立执行和追溯。
8. 多个大/小里程碑可以按依赖持续推进，失败能够回到正确真源、任务包或里程碑节点。
9. 新需求、漏项、技术风险和验收失败能够进入变更分流，不污染当前闭环或历史验收。
10. 每个目标版本完成后都有集成、交互和产品验收以及交付归档；含 UI 分支时才追加 UI 还原验收。
11. 主对话关闭、压缩或重开后，系统可以从项目真源、控制台账和最小检查点恢复，不依赖完整聊天历史。
12. 连续实施版本链中的全部必需能力均已交付，`Final Acceptance` 通过，范围外与后置事项已明确，`PC-20.AR` 已完成或由用户基于失败证据明确豁免，用户确认项目可以完全关闭。

Backlog 中存在可选增强或明确后置事项，不自动阻止项目完成；任何未交付的完整项目必需能力都会阻止 `Final Acceptance`。

## 8. 连续版本推进规则

- 每个版本是工程检查点和受控交付段，不是完整产品范围的删减授权。
- 已确认的完整项目必需能力不得因未进入 V1 而降级为不确定 Backlog。
- 每项必需能力必须唯一映射到一个主交付版本，并可被后续版本的回归与最终验收引用。
- 当前版本门禁通过后，默认准备并启动下一版本；若下一版本涉及新的路线、范围、安全、显著成本或不可逆决策，仍需用户确认。
- 任一版本失败时停在明确退回入口，不跳过该版本进入后续版本。
- 只有 `Final Acceptance` 可以给出整个项目“完成”的结论；普通版本只能给出该版本通过、退回、需讨论或阻塞。

## 9. Backlog 与范围外边界

- Backlog：不影响完整项目完成的可选增强，或经变更分流明确后置且不属于当前完整范围的事项。
- 范围外：当前产品明确不做或需独立项目重新进入需求入口的事项，不构成 NextStep 的未来交付承诺。
- 当前范围外至少包括：当前不进入主路线的 Web/UI 候选分支、Project Provenance Store、长期 Agent 贡献归因、Agent 市场、通用复杂多 Agent 编排平台、大而全知识库平台，以及未经变更分流的团队协作能力。
- 已确认核心能力不得通过改名进入 Backlog 或范围外清单。

### 10.2 覆盖字段冻结表

验收类型缩写：`I` 为集成验收，`X` 为交互验收，`P` 为产品验收。NextStep 自身当前主路线始终按 headless 的 `I/X/P` 验收；不得因为支持条件性 UI 规则而要求 NextStep 自身提交 UI 设计真源或 UI 还原证据。

Acceptance Profile 适用性只能由目标项目已接受路线决定：目标项目为 headless 时使用 `headless` Profile；目标项目已接受含 UI 路线时才追加 UI 设计真源和 UI 还原证据要求；Profile 与目标项目路线冲突时必须拒绝配置并阻塞推进。独立验收任务只能提供证据、校验证据引用和记录结论，不能声明或改变 UI 适用性。

P3 文档、现有 PRD、原型、S3/S4 真源和本仓库人工计划均为 bootstrap 输入或规划真源，不是未来版本的产品交付完成证据。任一实施版本通过，必须证明可运行的 NextStep 能力在目标项目 fixture 上完成对应行为，并提供正例、负例、阻塞、恢复和验收证据。

## 12. 覆盖冻结前已确认口径

以下口径均已确认，覆盖表冻结前不再保留待裁决项：

1. **条件性 UI**：当前只实现和验收 Acceptance Profile 的条件规则、配置校验和门禁记录，不实现 UI 设计源、UI 还原工具或 NextStep Web 界面。
2. **Acceptance Profile 三条规则**：
   - `headless`：必须执行集成验收、交互验收和产品验收。
   - 含 UI：在集成、交互和产品验收之外，额外要求 UI 设计真源和 UI 还原证据。
   - Profile 与路线冲突：拒绝配置并阻塞推进，不得降级为警告或继续执行。
3. **UI 证据职责边界**：UI 设计真源只能来自目标项目已接受的含 UI 路线；独立验收任务只能提供或采集 UI 还原证据、校验证据引用并记录结论，不能声明或改变 UI 适用性。NextStep 只校验 Profile 适用性、证据引用和门禁结论，并记录结果。

另有以下口径已由较晚且更具体的已会签真源裁决，不作为待决项：

- 主对话承载 Skill 交互但不读写项目；项目解析、真源读写和验证由隔离的集成/执行任务完成，只返回最小摘要。
- 正式门禁统一为 `通过 / 退回 / 需讨论 / 阻塞`；延期和变更是原因或分流路径，不是第五种正式结论。
- 进入 NextStep 与正式确认需显式用户动作；用户确认计划后的普通后台任务可以默认安静地自动分派。
- 大里程碑验收与目标交付段汇总验收分别保留；集成、交互和产品验收即使写在同一报告中也必须分区给出证据和结论。
- 用户可以作为外部执行者提交产物，但该产物必须进入与 Agent 产物相同的不可变候选、独立验证和五类结论链。
- P3 的规划输入按当前上游真源集合执行，不沿用 004 中仅以 PRD 或版本路线作为输入的早期窄口径。
- PC-02 的“需求恢复”仅指从真源重载同一冻结状态；修改冻结需求必须进入 PC-17，形成新候选并重新会签。
- 覆盖表以 `PC-01..PC-20` 为唯一主键；004 的 16 项能力作为强制来源映射与反向矩阵，确保已会签能力零遗漏。
- PC-04 的“原型”是载体无关的产品流程与交互模型，覆盖输入、回应、确认节点、阶段转换、异常与恢复；不建设 NextStep Web/UI，也不窄化为 Codex 对话脚本。
- Final Acceptance 要求至少一个正式支持的主宿主通过 `full`；其他声明支持的宿主至少通过 `manual-isolated`；`blocked` 环境不得列为受支持或可交付。`manual-isolated` 只作为兼容或故障降级模式，不是完整产品的最高交付形态。
- 项目交付清单与正式证据是 Final Acceptance 硬门禁；宿主任务归档失败不反转已成立的 `PC-20.FA`，但 `PC-20.AR` 保持待归档，项目不得标记为完全关闭，直到重试成功或用户基于失败证据明确豁免。

## 19. 拆解顺序

1. 重审 P1 蓝图中的版本示例和全部能力，先划定不可偏离的完整项目终态。
2. 建立完整项目必需能力覆盖表和最终完成定义，区分必需能力、可选增强与范围外事项。
3. 比较连续版本链的切分方式，以依赖、集成边界和风险顺序决定版本数量，不以首版速度或 MVP 范围为裁决标准。
4. 把每项必需能力唯一分配到 `V1 / V2 / V3 / ...` 的主交付版本，并建立 `Final Acceptance` 汇总门禁。
5. 将所有实施版本拆成可集成验收的大里程碑，再拆成可独立验证的小里程碑，不只拆 V1。
6. 为全部小里程碑补齐输入、输出、DoD、测试、依赖和退回规则。
7. 建立量化指标与全量追踪矩阵，检查每个上游需求、架构风险和最终完成条件都有承接位置。
8. 完成字段自查、范围扫描和独立规划审查后提交用户会签。
