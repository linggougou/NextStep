# 项目上下文摘要（S3 UI 设计真源）

生成时间：2026-07-08 00:00:00

## 1. 相似实现分析

- **实现 1**：`docs/design-docs/p2-product-prototype.md`
  - 模式：先定义页面清单、主流程、关键交互和不可偏离项，再用表格和流程图表达阶段边界。
  - 可复用：核心页面命名、项目驾驶舱优先原则、门禁结论口径、不可偏离项清单。
  - 需注意：P2 只定义原型，不冻结视觉和技术内容；S3 需要承接但不能越界到 S4/P3。
- **实现 2**：`docs/design-docs/p2-ui-design-source-requirements.md`
  - 模式：按“必须覆盖的页面 -> 必须表达的核心信息 -> 组件状态 -> 响应式 -> 验收输入”组织内容。
  - 可复用：页面范围、状态范围、信息密度要求、移动端不能退化成聊天流的约束。
  - 需注意：S3 必须把输入要求落成可验收真源，而不是重复要求清单。
- **实现 3**：`docs/product-specs/005-stage-document-contracts.md`
  - 模式：先定义文档定位，再列必填字段、合格标准和禁止提前写入内容。
  - 可复用：S3 必填字段、设计稿链接/截图证据/设计版本号证据链、禁止提前写入清单。
  - 需注意：S3 必须只写 UI 设计真源和验收依据，不能带入技术栈、API、数据库、版本路线或执行任务包。

## 2. 项目约定

- **命名约定**：阶段文档使用 `s3-ui-design-source` 这类 kebab-case 文件名；标题与正文使用简体中文。
- **文件组织**：设计真源放在 `docs/design-docs/`；执行计划放在 `docs/exec-plans/active/`；操作和验证留痕放在 `.codex/`。
- **导入顺序**：当前阶段均为 Markdown 文档，无代码导入要求。
- **代码风格**：文档偏向“定位 -> 必填内容 -> 边界 -> 验收”的结构，使用短段落、表格和清单。

## 3. 可复用组件清单

- `docs/design-docs/p2-product-prototype.md`：复用核心页面清单、门禁口径、不可偏离项。
- `docs/design-docs/p2-ui-design-source-requirements.md`：复用页面覆盖范围、组件状态要求、响应式要求。
- `docs/product-specs/005-stage-document-contracts.md`：复用 S3 必填字段和禁止提前写入边界。
- `docs/exec-plans/active/s3-ui-design-source.md`：复用本阶段 DoD 与非目标。
- `PROJECT_ROUTE_LOCK.md`：复用当前阶段目标、可验收交付物和门禁出口。

## 4. 测试策略

- **测试框架**：当前阶段无代码测试框架，采用文档一致性与边界扫描验证。
- **测试模式**：文档存在性检查、字段覆盖检查、禁写内容扫描、占位残留检查、`git diff --check`。
- **参考文件**：`.codex/verification-report.md`
- **覆盖要求**：覆盖正常字段、证据链字段、禁止提前内容和阶段状态一致性。

## 5. 依赖和集成点

- **外部依赖**：无强制外部设计工具依赖。
- **内部依赖**：依赖 `P2 产品原型`、`P2 UI 设计真源输入要求`、`P2.1 后续真源文档契约`、`PROJECT_ROUTE_LOCK.md`。
- **集成方式**：S3 文档作为后续 UI 还原验收依据，被 `PLANS`、路线锁、验证报告引用。
- **配置来源**：当前阶段配置与边界来自 `PROJECT_ROUTE_LOCK.md` 和 `docs/PLANS.md`。

## 6. 技术选型理由

- **为什么用这个方案**：当前阶段目标是冻结 UI 设计真源和验收口径，Markdown 文档最适合保持可追溯、可差异比对和可会签。
- **优势**：证据链清晰；可直接链接到页面细节、状态表和验收清单；不会误导为技术实现。
- **劣势和风险**：没有外部高保真视觉稿时，必须用结构快照和文案规则补足还原依据。

## 7. 关键风险点

- **并发问题**：无代码并发风险，主要风险是多文件状态不一致。
- **边界条件**：容易误写技术栈、API、版本路线或执行任务包，需要在正文和验证中双重防护。
- **性能瓶颈**：无运行时性能问题。
- **安全考虑**：本轮不涉及权限、认证、加密或外部服务接入。
