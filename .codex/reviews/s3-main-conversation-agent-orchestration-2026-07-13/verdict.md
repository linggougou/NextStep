# 结论

`REVISE`，独立评分 `84 / 100`。三层职责与上下文隔离方向成立，但当前书面设计尚不足以进入四份正式材料迁移。

# 为什么

1. 依赖任务调度链不闭合。集成准备任务把任务包写入任务注册表，后续测试与审查任务要求“依赖满足后由主对话创建”；但主对话不得读取项目文件，又默认不接收普通任务状态。当前没有定义谁向主对话发送最小 `dispatch-ready` 控制信封，也没有确认、幂等和恢复规则。
2. 独立验证没有覆盖精确最终集成产物。测试和审查验证候选产出后，集成 Agent 仍可能因冲突处理改变内容；当前只规定集成 Agent 运行整体验证，却又禁止其自我批准。正式状态可能基于未经独立验证的合入结果提升。
3. Codex 宿主能力被写成既成保证。当前会话能确认独立项目任务、worktree、线程读取和归档工具存在，但自动内部任务创建、从任意候选快照启动、角色级只读强制和依赖满足自动触发并没有被统一能力契约证明。
4. CR 002 缺少上述运行时风险、验证成本、迁移失败回滚和能力不可用时的降级或阻塞策略。

# 必须修改

- 增加内部控制面消息契约：`dispatch-ready` 信封至少包含任务 ID、任务包引用、项目/环境、不可变基线、依赖证据、去重键、过期条件和确认状态。它可进入主对话 Agent 的最小控制上下文，但不得成为用户可见执行噪声。
- 调整集成顺序：候选产出物化为不可变提交或等价快照，独立验证该候选；集成后若内容或基线发生任何变化，必须对精确集成提交/快照再次独立验证，通过后才能更新正式真源和阶段状态。
- 增加宿主能力预检与降级表。能力缺失时只能转为用户显式创建任务、串行同任务执行、人工提供候选引用或阻塞，不得声称仍满足严格隔离。
- 在 CR 002 中补齐风险、验证成本、迁移/回滚和能力不可用处理。
